# The blog on the app road: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `www.<domain>` serves a Hugo/PaperMod site built by the golden path from Forgejo's `ci/blog`. Kargo promotes
it by itself, and Argo Rollouts releases it blue-green. Until `ci/blog` exists, a "coming soon" page shows, and the
apex redirects to `www` through OpenTofu.

**Architecture:**
- A Backstage template `hugo-site` gives `ci/blog` its skeleton.
- `apps/blog.yaml` becomes a road app like `test/fixtures/apps/delivery-test.yaml`, but blue-green:
  - a new pre-promotion check, `static-site-responds`, fetches the preview's page and its assets;
  - `gateway-success-rate` runs after the switch.
- The "coming soon" page is a ConfigMap mounted through app-template's `persistence`. The release file Kargo writes
  turns it off, so it never shadows the real site.
- `infra/_modules/cloudflare` adds the apex record and a Redirect Rule.
- A sandbox group `blog` and a spec `Blog` drive it end to end.

**Tech Stack:** Hugo (extended), PaperMod, static-web-server, app-template 5.3.0, Argo Rollouts (`blueGreen`), Kargo
1.12, OpenTofu (Cloudflare provider v5) with `tofu test`, Ginkgo e2e, Go offline tests (testify).

**Spec:** `docs/superpowers/specs/2026-11-21-blog-design.md`

## Global Constraints

- Latest stable release of every tool and image, pinned exactly, with no `latest` (CLAUDE.md). Look up each version
  when you write it; the repo's versions are not a reference.
- The canonical name is `www.<domain>`; the apex redirects there with a 301, keeping the path and query.
- Release blue-green, never a canary, with two replicas; auto-promotion on (Kargo's both stages, and the Rollout).
- The final image holds only the site and `static-web-server`, runs as a numeric non-root user and listens on 8080.
- No personal data in this repository: the template holds placeholders only.
- The road's lists name `blog`: Kargo `projects`, `zotPull`, `registry.puller` destinations, `rotationReaders`,
  `publicKeyReaders`, the rotation catalog and OpenBao's policy `rotator`.
- The sandbox group `blog`: components `[apps/blog.yaml]`, needs `[delivery]`, labels `[blog]`.

## Review Focus

1. **The real site shadowed by the "coming soon" page after the first promotion.** Expected: the release file turns the
   mount off. Pinned in Task 3 (`TestBlogReleaseDropsComingSoon`).
2. **A page naming an asset on another origin** (a CDN font, an absolute `https://` link). Expected: the preview check
   fetches only same-origin assets and ignores the rest. Pinned in Task 1 (`TestStaticSiteRespondsChecksAssets`, its
   fixture).
3. **A request to the apex with a path and query** (`hoangduong.dev/posts/x?a=1`). Expected: `www.hoangduong.dev/posts/x?a=1`
   with a 301. Pinned in Task 4 (the `redirect` run).
4. **A repository created from the template under another name than `blog`.** Expected: it builds `registry/<name>`, which
   no Warehouse watches. The guide says the name must be `blog`, and the template's description says so. Pinned in
   Task 2 (the template's description test).
5. **A theme archive whose hash changed upstream.** Expected: the build fails rather than ship an unchecked theme.
   Pinned in Task 2 (the Containerfile names a sha256 and checks it).

### Task 1: The pre-promotion check `static-site-responds`

**Files:**
- Modify: `system/argo-rollouts/templates/analysis-template.yaml` (a second `ClusterAnalysisTemplate`
  `static-site-responds`)
- Create: `system/argo-rollouts/files/static-site-responds.sh` (the Job's script, read into the template with
  `.Files.Get`)
- Test: `test/offline/argo_rollouts_test.go`, `test/offline/static_site_responds_test.go`

**Interfaces:**
- Produces: `ClusterAnalysisTemplate` `static-site-responds`.
  - Args: `service`, `namespace`, `port` (default "80").
  - One metric, `assets`, with a `job` provider, `count: 1`, `failureLimit: 0`.
  - Pod as `canary-responds`' (non-root 65532, RuntimeDefault, no token, read-only root, `images.curl`).
  - The Job runs `static-site-responds.sh`, with the URL `http://<service>.<namespace>:<port>/` in env `URL`.
- Produces: the script reads `URL`. It fetches the page and then every same-origin `href`/`src` of `<link
  rel=stylesheet>`, `<script>`, `<img>` and `<link rel=icon|preload>`: relative paths, or absolute ones with the
  page's host. It prints each non-2xx and exits 1 if there is any. It exits 0 when everything answered 2xx, ignoring
  other origins.

- [ ] **Step 1: Write the failing tests**
  - `TestStaticSiteRespondsRender` (`argo_rollouts_test.go`):
    - the template exists with args `namespace,port,service`;
    - its metric `assets` has `failureLimit` 0 and `count` 1;
    - the pod's `securityContext.runAsNonRoot` is true;
    - the container's image equals `canary-responds`' image.
  - `TestStaticSiteRespondsChecksAssets` (`static_site_responds_test.go`) runs the script against an
    `httptest.Server` (Go) in three cases:
    1. a page naming `/css/a.css`, `js/b.js` and `https://fonts.example.com/f.css` → exit 0, and no request reaches
       the other origin;
    2. the same page with `/css/a.css` answering 404 → exit 1, with the output naming `/css/a.css`;
    3. the page itself answering 500 → exit 1.
- [ ] **Step 2: Run** `go -C test test ./offline -run 'StaticSiteResponds'`. Expected: FAIL (no template, no script).
- [ ] **Step 3: Implement** the template and the script (POSIX `sh`, curl, `grep -o`/`sed`; the curl image has no
  other tools; check this in the test by running it under `sh`).
- [ ] **Step 4: Run** the tests again. Expected: PASS. Also run `scripts/ci-check render` and `scripts/ci-check policy`.
- [ ] **Step 5: Commit** `feat(argo-rollouts): static-site-responds checks a blue-green preview's page and its assets`
