# k3d Sandbox and Istio Gateway Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The sandbox runs on k3d and production on k3s defaults, Cilium leaves the repo, and Istio serves the Gateways `istio-system/gateway` and `istio-system/public`; `make dev` passes 72/72 from scratch.

**Architecture:** `metal/` creates a one-server k3d cluster (k3s v1.37.1, traefik off) whose load balancer publishes host ports 80/443/22, with the Gateway API CRDs in k3s's auto-deploy manifests; production's Ansible k3s role drops its Cilium-specific flags and gets kube-vip v1.2.4 with a service load balancer for one class. A new wrapper chart `system/istio-system` (Istio `base` + `istiod` 1.31.1, two Gateways, the wildcard certificate, the redirect route, a sandbox-only CoreDNS rewrite) replaces `system/gateway`, and every route moves to the new Gateway names.

**Tech Stack:** k3d 5.9.0, k3s v1.37.1+k3s1, Istio 1.31.1, Gateway API v1.6.3 (standard channel), kube-vip v1.2.4, Ansible, Helm wrapper charts, Argo CD, Go tests.

**Spec:** `docs/superpowers/specs/2026-10-14-k3d-istio-design.md`

## Global Constraints

- Versions, pinned exactly: k3d 5.9.0 (nixpkgs-unstable), `rancher/k3s:v1.37.1-k3s1` / `v1.37.1+k3s1`, Istio charts `base` and `istiod` 1.31.1 from `https://blob.istio.io/istio-release/charts`, Gateway API `v1.6.3` `standard-install.yaml`, `ghcr.io/kube-vip/kube-vip:v1.2.4`.
- Gateway names: `istio-system/gateway` (LAN, listeners `http` 80, `https` 443, `ssh` 22) and `istio-system/public` (Tunnel, `https` only, Service `ClusterIP`); certificate secret `wildcard-tls`; generated Services `gateway-istio` and `public-istio`.
- `global.publicGateway`: `public` in production, `gateway` in the sandbox.
- Production kube-vip: API VIP `192.168.1.100` as before; service load balancer only for `loadBalancerClass: kube-vip.io/kube-vip-class`; Gateway `gateway` on `192.168.1.224`, wireguard on `192.168.1.225`.
- The sandbox has no kube-vip: the Gateway Service has no class there and ServiceLB publishes it.
- No `cilium`, `homelab-public`, `cilium-gateway-*` or `namespace: gateway` reference may remain outside `docs/superpowers/` (history).
- Spec deviations already ruled while planning (recorded in Task 3's commit message and the spec): Gateway API **standard** channel (v1.6.3 ships `TCPRoute` there, and Istio 1.31 serves `TCPRoute` and `BackendTLSPolicy` without `PILOT_ENABLE_ALPHA_GATEWAY_API`), so the alpha flag is not set; the Gateway's production IP is the kube-vip annotation `kube-vip.io/loadbalancerIPs` on its Service (through the `parametersRef` ConfigMap) instead of `spec.addresses`.
- Istio's chart repository is `https://blob.istio.io/istio-release/charts` (the old `istio-release.storage.googleapis.com` index stops at 1.30.5 and 1.31 release candidates); a scratch render of `base` + `istiod` 1.31.1 from it gave `docker.io/istio/pilot:1.31.1`, `pilot.resources` applied, and the webhooks `istiod-default-validator` and `istio-validator-istio-system`.
- Spike done while planning (2026-10-14): a k3d cluster with `18080:80@loadbalancer` answered `200` on `127.0.0.1:18080` and `localhost:18080` from WSL (mirrored, `loopback0` present), and kubectl reached its API on `0.0.0.0:<port>`, so no socat and no kubeconfig rewrite are needed.
- Branch `feat/k3d-istio` from `dev`, PR into `dev`; ask before merging. `KUBECONFIG=$PWD/metal/kubeconfig.yaml` for kubectl.

## Review Focus

1. Argo CD drift on Istio's webhooks: istiod patches `caBundle` and `failurePolicy` into its `ValidatingWebhookConfiguration`s, which would keep `istio-system` OutOfSync or flap. Expected: Synced and stable. Pinned in Task 3 (ignore rule in `argocd-cm` plus `RespectIgnoreDifferences=true`) and checked in Task 7 (the Argo CD sync check).
2. First sync ordering on a fresh cluster: Gateways need the `istio` GatewayClass, which istiod creates after it starts. Expected: Argo CD retries until the Gateways are accepted; no manual step. Checked in Task 7 (fresh `make dev`).
3. CoreDNS rewrite: `coredns-custom` must be picked up by k3s's CoreDNS without editing the Corefile, or every pod-to-Kanidm call fails. Pinned in Task 3 (render check of the ConfigMap key `nip-io.override`) and checked in Task 7 (identity and SSO tests).
4. Host port 22 on WSL: the k3d load balancer binds `0.0.0.0:22`; a host `sshd` would block cluster creation. Expected: `metal/Makefile` refuses to start with a clear message when 80, 443 or 22 is taken. Pinned in Task 1.
5. Production render: no Cilium flag left in the k3s config, kube-vip serves only its class, the Gateway Service gets the class and IP annotation in production and neither in the sandbox. Pinned by the render checks in Tasks 2 and 3.
