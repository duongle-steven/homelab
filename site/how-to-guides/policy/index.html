    Policy: Kyverno and Pod Security Admission

    Two layers keep workloads within the rules (step 15b, docs/superpowers/specs/2026-10-27-policy-design.md).

    • Kyverno (system/kyverno) applies the Pod Security Standards at restricted, plus two rules of this repository: every image is pinned (a tag other than latest, or a digest), and comes from an allowed registry (registries in system/kyverno/values.yaml, plus zot). It runs in Audit: violations land in PolicyReports; nothing is refused yet (Enforce is step 15b-2).
    • Pod Security Admission (Kubernetes itself) enforces baseline on every managed namespace, and stays in force if Kyverno is down. Namespaces whose pods need the node are privileged: the mesh (istio-system), Ceph (rook-ceph), opentelemetry (its agent), monitoring-system (node-exporter), the sandbox's csi-hostpath, and the VPN routers (tailscale, wireguard). The labels come from Argo CD's ApplicationSets (system/argocd/values.yaml).

    The policy check

    scripts/ci-check policy (a basic check, also in CI) renders every chart and app file for both environments and runs the same policies with the kyverno CLI. A pull request whose workload breaks one fails before it merges.

    A new workload

    Set its securityContext:

    • The pod: seccompProfile: {type: RuntimeDefault}, and runAsNonRoot: true with the image's numeric user (runAsUser, runAsGroup, fsGroup) when the image has a non-root user.
    • Each container: allowPrivilegeEscalation: false, and capabilities: {drop: [ALL]} when it runs as non-root.

    In app files, use defaultPodOptions.securityContext and each controller's defaultContainerOptions (defaultContainerOptionsStrategy: merge).

    An exception

    When the image cannot meet a rule (it runs only as root, it needs the node), write a PolicyException beside the workload, in its own chart (templates/policy-exception.yaml) or app file (rawResources.policy-exception):

    apiVersion: policies.kyverno.io/v1
kind: PolicyException
metadata:
  name: pod-security
  annotations:
    homelab/reason: "the image runs as root (no USER)"
spec:
  policyRefs:
    - {name: require-run-as-nonroot, kind: ValidatingPolicy}
  matchConditions:
    - name: app
      expression: "object.metadata.name.startsWith('app')"

    Name only the policies it breaks, and match only its workload by name. Read the current exceptions with kubectl get policyexceptions.policies.kyverno.io -A. If the workload also breaks baseline (hostPath, host namespaces, privileged, added capabilities), its namespace must be privileged in Argo CD's templatePatch.

    Reports

    kubectl get policyreports -A                      # one per resource (its scope)
kubectl -n <namespace> get policyreports -o yaml  # each result: fail, error or warn (passes are not kept)

    TestPolicy checks that no workload of this repository fails. That is the condition for switching to Enforce.

    On a fresh cluster a pod can start before Kyverno has cached the PolicyException beside it, so its report (and its Deployment's) shows a fail the exception excuses, until the next background scan (every 6 hours in the sandbox, every hour in production) or the pod is recreated. TestPolicy therefore judges only the reports of pods created a minute after the newest exception was created or changed (k3s's own pods in kube-system are not the repository's). On a fresh sandbox that is few pods (often only CronJob runs): there TestPolicy does not prove the renders clean, scripts/ci-check policy does. Before Enforce (15b-2), read the reports of a sandbox that has run a background scan since its first sync.
