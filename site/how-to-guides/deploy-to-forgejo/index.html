    Deploy to Forgejo

    GitHub is where work happens (pull requests, checks, the sandbox). Production's Argo CD syncs ops/homelab on Forgejo, which changes only when a commit is deployed:

    just infra deploy production       # the infrastructure, Forgejo's orgs ops and ci, the push, the Argo CD bootstrap
cd cli && go run ./cmd/lab infra forgejo push   # only the push

    Both refuse anything but origin/master checked out without changes (and no untracked file under infra/ or system/argocd/) whose check checks passed and whose merged pull request's check sandbox passed (lab infra forgejo verify). Nothing force-pushes: roll back with a revert through a pull request.

    What proved the release

    infra/production/cluster/config.json names the environment that proves a release: "release_proof": "testbed" or "staging"; without the key verify refuses. A release changing what that environment runs needs a commit carrying its mark, the commit status of that name, written when just testbed passes: infra/testbed/release-paths.yaml's paths and the components system/argocd/values-testbed.yaml lists, less not_run. A mark on an earlier commit, a merged branch's tip included, counts when those paths are the same. verify always says how far the testbed goes: "only the testbed proved this: no production-like environment did".

    Without the mark verify refuses and names the paths; just infra deploy production --skip-proof "<reason>" (--skip-proof=<reason>) releases anyway and records the reason as the commit status testbed/skipped, which proves nothing to a later release.

    What lab infra forgejo sync owns

    sync (part of just infra deploy production) owns orgs ops and ci, ci's bot and its webhook; nothing declares other orgs, teams or repositories. Running it again keeps what is right, fixes what is wrong and creates what is missing:

    • orgs ops and ci, private (made private again if someone changed that);
    • ops/homelab, private, default branch master, created empty: the first deploy fills it;
    • local users deploy (write) and argocd (read), restricted to the repositories they collaborate on; sync refuses a user of that name who signed in with Kanidm, and a team granting either of them more;
    • master's protection: only deploy may push, nobody force-pushes or deletes it, Forgejo's site admins included (they can still edit the protection, which the next sync restores);
    • their tokens in OpenBao: secret/forgejo/deploy (the push) and secret/argocd/forgejo (Argo CD's read-only credential, argocd-repo-forgejo);
    • in org ci, its team developers (write on code and pull requests, may create repositories in ci, not all of them): Forgejo's Kanidm login source makes homelab-admins its owners and homelab-editors its developers; no team of ci reaches ops;
    • the local user ci-bot, alone in ci's team pipeline (write on code of every repository of ci: the golden path's clones and commit statuses), and its token in secret/ci/forgejo-token;
    • ci's webhook to Argo Events (http://forgejo-eventsource-svc.ci:12000/forgejo, push and pull request events, Authorization: Bearer with secret/ci/generated/webhook), rewritten when that secret or the hook changed (In-cluster CI).

    Other repositories (for example the blog) live in org ci, created there or mirrored, not through push.

    Break-glass: GitHub or the internet is down

    Production keeps running without GitHub: Argo CD reads Forgejo. A fix that cannot wait for GitHub skips verify's GitHub checks, and nothing else:

    direnv exec . scripts/ci-check all             # the checks GitHub would have run, locally
git switch -c fix/<what> && git commit ...     # a branch: master stays GitHub's
just infra deploy production --break-glass "<why>"  # verify without GitHub, the infrastructure, sync, the push, the bootstrap

    Before anything is applied, verify --break-glass still refuses uncommitted changes, untracked files under infra/ or system/argocd/ and a commit that does not descend from what ops/homelab's master holds (so production never runs infrastructure from a commit the push would then refuse); the push prints the reason. --break-glass cannot be combined with --force. When GitHub is back, push the branch and open a pull request into dev that says why, then the release pull request into master: merge commits only (never squash or rebase), so master contains the deployed commit and the next normal deploy fast-forwards.

    What still depends on the internet:

    • OpenTofu's state is on R2: with no internet just infra deploy cannot run. Push alone: cd cli && go run ./cmd/lab infra forgejo push --break-glass="<why>".
    • Charts served from *.github.io (app-template, Argo CD's) and images on ghcr.io are GitHub too: Argo CD renders only charts its repo server still caches, and a node runs only images it already pulled.
    • Kanidm and Forgejo work on the LAN; Cloudflare's Tunnel (the public routes) does not.

    The last resort, when nothing can be pushed: pause the Application's auto-sync in Argo CD (an admin, in its UI), change the resource with kubectl, then commit the same change and resume auto-sync once it is deployed; Argo CD would revert a manual change while auto-sync runs.
