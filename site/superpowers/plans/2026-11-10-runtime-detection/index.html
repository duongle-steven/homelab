    Runtime Detection (15g) Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Falco runs in every environment and only detects. Its events reach Loki and alert through Alertmanager, and a stalled Falco alerts too.

    Architecture: - Chart: system/falco is a wrapper chart of falcosecurity/falco: - the modern_ebpf driver, JSON events to stdout from warning up, no falcoctl; - accepted events rendered from values.yaml's accepted list into a rules file of its own. - Event alerts: Alloy already ships the pods' logs to Loki, and system/loki/files/falco-rules.yaml alerts on them. - Health alerts: a PrometheusRule in system/falco alerts on Falco's health from its metrics. - Proof: Ginkgo specs on the sandbox and the testbed.

    Tech Stack: Helm wrapper charts, Argo CD ApplicationSets, Loki ruler (LogQL), Prometheus rules, Go (testify, Ginkgo v2).

    Spec: docs/superpowers/specs/2026-11-10-runtime-detection-design.md

    Global Constraints

    • Versions: the latest stable falcosecurity/falco chart and Falco image, pinned exactly. When this was written: chart 9.2.2, Falco 0.45.2. Check upstream when building (CLAUDE.md, Rules).
    • Detection only: no Falco Talon, no falcosidekick, no k8s-metacollector, no Tetragon.
    • No runtime downloads: falcoctl.artifact.install.enabled: false and falcoctl.artifact.follow.enabled: false. Rules come from the image's stable ruleset plus files vendored in system/falco/files/.
    • Driver and output: driver.kind: modern_ebpf, falco.json_output: true, falco.priority: warning.
    • Alert severities: critical, alert and emergency events alert with severity critical. error events alert with severity warning. warning events show only on the dashboard. Alerts are grouped by rule and namespace.
    • The sandbox keeps every event and alert, as production does. Only the clean-baseline check counts events that have a Kubernetes namespace. A noisy workstation process is accepted in values-dev.yaml, never in values.yaml.
    • Every accepted event has a non-empty reason.
    • Namespace falco: privileged under Pod Security Admission and in the mesh, with an allow for Prometheus on the metrics port. No new egress.
    • The testbed:
    • no PolicyException, ServiceMonitor or PrometheusRule there (their CRDs are missing);
    • Falco is listed as a layer in values-testbed.yaml.
    • If it breaks the testbed's bar, Falco goes to not_run, its proof becomes one recorded manual run, and the VM sizes stay.
    • Commits end with the session's Co-Authored-By and Claude-Session lines.

    Review Focus

    1. Falco's own startup lines are not JSON. Every LogQL expression drops lines that fail | json (__error__=""), so a restart never fires or breaks an alert. Pinned in Task 2's TestFalcoLokiRules (the expressions carry __error__="").
    2. An accepted entry must narrow a rule without disabling it. The template renders a Falco exceptions: append on the named rule, never enabled: false. Pinned in Task 1's TestFalcoAccepted.
    3. Events from the workstation have no k8s.ns.name. The alert expressions group by namespace and still fire with an empty namespace. The baseline query filters namespace!="". Pinned in Task 2's test (the expression has no namespace filter).
    4. A node whose Falco pod is missing is caught by FalcoNotRunning (desired versus ready on the DaemonSet), not only by a failed scrape. Pinned in Task 2's TestFalcoPrometheusRules.
    5. The testbed's render has none of the kinds whose CRDs it lacks. Pinned in Task 1's TestFalcoRender (testbed case).

    • FalcoCriticalEvent matches priority=~"Critical|Alert|Emergency"; FalcoErrorEvent matches priority="Error".

    • Step 2: Run it. go test -C test ./offline/ -run TestFalcoLokiRules -count=1 → FAIL.
