    Step 11a: Backups Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Volume data that is not in git survives mistakes (hourly local snapshots) and the loss of every node (daily copies on R2), and comes back only by a command.

    Architecture: - Velero (system/velero) backs up labelled PVCs only, through CSI snapshots and its data mover (Kopia), to an S3 bucket: R2 in production, an in-cluster S3 server in the sandbox. - Local snapshots: an hourly CronJob takes plain VolumeSnapshots and prunes them, with no dependency on the internet. - The sandbox gets CSI snapshots from csi-driver-host-path and runs Forgejo on CloudNativePG, so the sandbox proves the same path production uses. - lab backup (cli/internal/backup) pushes, lists, enables and restores.

    Tech Stack: - Velero with velero-plugin-for-aws; - csi-driver-host-path and snapshot-controller (sandbox); - versitygw (sandbox S3); - CloudNativePG; - OpenTofu (infra/_modules/backup, Cloudflare provider); - Go: cobra, client-go dynamic, fake clients in tests; - the Go sandbox tests in test/.

    Spec: docs/superpowers/specs/2026-10-22-backups-design.md (the changes of Task 0 are written into it first).

    Global Constraints

    • Versions: latest stable release of every chart, image and tool, pinned exactly. Pin a digest when an image has no version tag. If Velero's chart ships an older app version than Velero's latest release, pin the image to the latest release.
    • Scope: backups hold PersistentVolumeClaims and their data only, never other Kubernetes resources.
    • Groups:
    • daily (off-site every day, plus local snapshots): OpenBao, Kanidm, Forgejo (forgejo-data and forgejo-db), Woodpecker's server, ntfy, Matrix (Dendrite and its PostgreSQL).
    • manual (off-site only through lab backup push, plus local snapshots): Actual Budget, paperless, OpenCloud.
    • none: zot, Loki, ollama, jellyfin, and everything else.
    • Local snapshots: hourly, kept 48 hours, taken and restored without the internet.
    • Off-site retention: 30 copies kept per schedule and per app (a count, never an age: see Task 0).
    • Restore: only by command. OpenBao and the apps come from the same backup run, and Forgejo's two volumes from the same run, snapshotted one right after the other.
    • Uploads of group manual: never without the person seeing the size first.
    • Credentials: the Kopia repository password and the R2 credentials live in OpenTofu's state on R2, never only in OpenBao.
    • Mesh and egress rules from CLAUDE.md hold (AuthorizationPolicy allow, port 15008 in a chart's NetworkPolicies, the webhook pod label). Velero's namespace gets egress 443 in production only.
    • No VolSync left anywhere: system/volsync-system, the privileged-movers annotation, the scopes.yaml entries, the docs.

    Review Focus

    1. A fresh install that is never restored and never enabled must keep its backups. A fresh install sees the bucket's old backups. Nothing may delete them, whether by expiry, prune or a schedule (Task 7's prune test and Task 9's TestBackup step "fresh state is read-only").
    2. A restore must not pick a backup the new cluster made of its own empty volumes. The default is the newest backup that completed before this cluster's creation (kube-system's creationTimestamp) (Task 9, TestPickBackupIgnoresOwnBackups).
    3. Argo CD must not undo a restore in progress. It must not scale the app back up or recreate an empty PVC while lab replaces it (Task 9, TestRestorePausesSync, and TestBackup).
    4. A PVC added later without a group must fail the basic checks, not silently stay out of the backups (Task 4, scripts/check-backup-groups with a fixture).
    5. The size prompt with no TTY or with --yes: lab backup push without a terminal and without --yes must refuse, not upload (Task 9, TestPushRefusesWithoutConfirmation).

    Task 0: Spec changes found while planning (needs the user's approval before Task 1)

    Files: - Modify: docs/superpowers/specs/2026-10-22-backups-design.md - Modify: CLAUDE.md (roadmap line 11a)

    Write these into the spec. These deviations were found while planning:

    1. Read-only by default instead of make infra restore=1 (decision 8).
    2. Velero is synced by Argo CD from git as soon as a cluster exists, before anyone can pass a flag. A forgotten flag would let a fresh install's Velero expire the old backups.
    3. So in git the backup location is ReadOnly and every schedule paused, and Argo CD ignores those two fields.
    4. lab backup enable switches them once: on a brand-new homelab, or after a restore was checked. lab backup disable switches back.
    5. A PrometheusRule fires when no backup succeeded for 26 hours. That also catches a cluster never enabled.
    6. Retention by count, not by age:
    7. Velero's own expiry is set far out (ttl: 87600h).
    8. A prune CronJob keeps the newest 30 completed backups per schedule and per app, and runs only while the location is ReadWrite.
    9. A cluster dead for months therefore loses nothing.
    10. Kanidm goes through Velero like every other volume (crash-consistent SQLite).
    11. kaniop 0.19's own backups (KanidmBackupSchedule) require their own S3 repository: a second restore path, as with CloudNativePG.
    12. If Task 2's spike shows kaniop cannot take a restored volume, fall back to kaniop's backups and say so in the PR.

    13. The sandbox gets CSI snapshots from csi-driver-host-path, its default StorageClass. Its S3 server is versitygw. Local snapshots and Velero's CSI data mover then run in the sandbox too; only Ceph's specifics stay on the production checklist.

    6. cnpg.io/hibernation=on;
    7. wait for no pods;
    8. cnpg.io/reconciliationLoop=disabled;
    9. delete the PVCs;
    10. restore;
    11. set each PVC's controller ownerReference to the Cluster (its current uid);
    12. remove the reconciliation annotation, then the hibernation annotation;
    13. restart Forgejo's pod, whose init container crash-looped while the database was down.
