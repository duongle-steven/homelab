    Secrets management

    Overview

    • OpenBao (platform/openbao) holds the cluster's secrets in its KV store secret/.
    • Every namespace reads its own branch, secret/<namespace>/<name>, through its SecretStore openbao (system/secret-store, rendered by every Application) and External Secrets ExternalSecrets. OpenBao refuses a read of another namespace's branch.
    • Values come from three places:
    • generated secrets: platform/generated-secrets pushes each one to its readers' branches, under secret/<namespace>/generated/, the only paths its role writer reaches;
    • OpenTofu's secrets (Cloudflare's tokens and Tunnel credentials, WireGuard's key, the backup bucket's credentials file and Kopia's repository password from infra/<env>/backup): the unit infra/<env>/secrets writes them as Secrets into namespace infra-secrets, and platform/infra-secrets pushes them anywhere except generated/ (role infra);
    • Kanidm's OAuth2 client secrets: the kaniop operator, directly in each client's namespace.
    flowchart TD
  subgraph generated-secrets[generated-secrets namespace]
    generators[Password generators] -- PushSecret generatorRef, IfNotExists --> writer[SecretStore openbao-writer]
  end
  writer -- role writer: generated/ --> openbao[(OpenBao secret/)]
  subgraph infra-secrets[infra-secrets namespace]
    tofu[OpenTofu infra/env/secrets] -- server-side apply --> tofusecrets[Secrets]
    tofusecrets -- PushSecret, Replace --> infra[SecretStore openbao-infra]
  end
  infra -- role infra: all but generated/ --> openbao
  subgraph app[application namespace]
    store[SecretStore openbao] -- role apps: secret/&lt;namespace&gt;/ --> openbao
    ExternalSecret --- store
    ExternalSecret -- create --> Secret
    App -- read --> Secret
  end

    Reading a secret

    apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: grafana-admin
spec:
  secretStoreRef:
    kind: SecretStore
    name: openbao
  data:
    - secretKey: password
      remoteRef:
        key: grafana/generated/admin  # secret/grafana/generated/admin: the namespace's own branch
        property: password

    scripts/check-secret-stores refuses, before merge, an ExternalSecret that reads another store or another namespace's branch, and a generated secret that nobody reads or that is read but never pushed. A secret two namespaces need is pushed to both branches (destinations in platform/generated-secrets/values.yaml).

    Unsealing and configuration

    • OpenBao unseals itself (seal "static") with a 32-byte key that the OpenTofu unit infra/<env>/openbao creates, keeps in its state (.state/, readable only by you; Cloudflare R2 with state encryption from step 8c) and writes into Secret openbao/openbao-unseal. Losing the key loses everything OpenBao holds.
    • On first start OpenBao configures itself from platform/openbao/values.yaml (initialize stanzas):
    • the KV v2 store secret/ and Kubernetes auth;
    • the policies apps (read secret/<namespace>/), writer (push: create, read, update on secret/<namespace>/generated/ only, because External Secrets reads before it writes; no delete), infra (the same everywhere except generated/), snapshot (read sys/storage/raft/snapshot) and admin;
    • their roles: apps for every namespace's default service account, writer for generated-secrets', infra for infra-secrets/openbao-infra, snapshot for openbao/openbao-snapshot (the hourly raft snapshot) and admin for openbao/openbao-admin. They accept only service account tokens issued for audience openbao (the SecretStores ask for it), so a token sent to OpenBao never works against the API server.
    • These stanzas run only on an empty storage: editing them later changes nothing on a running OpenBao. Apply the change by hand with the admin role (below), or, in the sandbox, just dev-clean.
    • No root token and no recovery keys exist.
    • OpenBao's data is backed up as its hourly raft snapshot (CronJob openbao/openbao-snapshot, volume openbao-snapshots), copied off-site daily (Backup and restore). The snapshot is useless without the unseal key, and the Kopia password that encrypts the copies lives in OpenTofu's state, never only in OpenBao.

    Emergency access

    No root token exists: log in with the admin role, as service account openbao/openbao-admin.

    # Logs the bao CLI in OpenBao's pod in with the admin role for an hour; neither token reaches an argument or your
# shell history
kubectl -n openbao create token openbao-admin --audience=openbao --duration=1h |
  kubectl -n openbao exec -i openbao-0 -c openbao -- \
    sh -c 'bao write -field=token auth/kubernetes/login role=admin jwt=- | bao login -no-print -'
kubectl -n openbao exec -it openbao-0 -c openbao -- sh
# Inside, when you are done
bao token revoke -self && rm ~/.vault-token

    The OpenBao token stays in ~/.vault-token in the pod until you revoke it, it expires or the pod restarts. Anyone who can create tokens for openbao-admin or exec into OpenBao's pod (cluster admins) holds every secret.

    Generated secrets

    Random secrets (admin passwords and other random app secrets; kaniop generates the OAuth2 client secrets) are listed in platform/generated-secrets/values.yaml. Each one is an external-secrets Password generator and a PushSecret that runs it (selector.generatorRef) and writes the value to each of its destinations in OpenBao (updatePolicy: IfNotExists): every reconcile (hourly, a force-sync, an ESO restart) generates a value and writes it only where none exists, so an existing value never changes and a missing one (an OpenBao that lost its data, a rotation) is written within the hour. The destinations of a first push all get the same value. Namespace generated-secrets holds no Secret: OpenBao's value is the only one. (Until step 8e a Secret in global-secrets held a copy: ESO's refreshPolicy: CreatedOnce regenerates under a stale cache, so the copy could differ from what every app reads.)

    ./platform/generated-secrets/values.yaml
    # Random secrets generated for this cluster and written straight into OpenBao, once per destination
# (secret/<namespace>/generated/<name>, the only paths the writer reaches): a Password generator and a PushSecret
# each (templates/), no Secret in this namespace. Readers use their namespace's SecretStore openbao. A value two
# namespaces need is two destinations of one entry, written by the same push; a destination added later gets the
# existing value by hand first (docs/concepts/secrets-management.md). Never rotated automatically.
secrets:
  - name: forgejo.admin
    key: password
    special: true
    destinations: [forgejo/generated/admin]
  - name: paperless.admin
    key: PAPERLESS_ADMIN_PASSWORD
    special: true
    destinations: [paperless/generated/admin]
  # paperless 3 refuses to start without it
  - name: paperless.secret-key
    key: PAPERLESS_SECRET_KEY
    length: 64
    destinations: [paperless/generated/secret-key]
  # Kiali signs its session cookies with it (AES: 32 characters)
  - name: kiali.signing-key
    key: key
    length: 32
    destinations: [kiali/generated/signing-key]
  - name: grafana.admin
    key: password
    special: true
    destinations: [grafana/generated/admin]
  # zot's machine account ci (its htpasswd) and the golden path's push (platform/ci)
  - name: registry.ci
    key: password
    destinations: [zot/generated/ci, ci/generated/registry]
  # Forgejo's org ci webhook to Argo Events (Authorization: Bearer, set by lab infra forgejo sync)
  - name: ci.webhook
    key: token
    destinations: [ci/generated/webhook]
  # ntfy (apps/ntfy.yaml): user alerts publishes (Alertmanager), user phone subscribes (people's apps). No symbols:
  # ntfy's lists are comma-separated. ntfy tokens are tk_ plus 29 characters: the readers add the prefix
  - name: ntfy.alerts-token
    key: token
    length: 29
    destinations: [ntfy/generated/alerts-token, monitoring-system/generated/ntfy]
  - name: ntfy.alerts-password
    key: password
    destinations: [ntfy/generated/alerts-password]
  - name: ntfy.phone-token
    key: token
    length: 29
    destinations: [ntfy/generated/phone-token]
  - name: ntfy.phone-password
    key: password
    destinations: [ntfy/generated/phone-password]
  # Argo CD's local account backstage (system/argocd-config bcrypts it into argocd-secret), and Backstage's Argo CD
  # plugin signing in with it
  - name: argocd.backstage-password
    key: password
    destinations: [argocd/generated/backstage-password, backstage/generated/argocd-password]
  # Backstage's session cookies
  - name: backstage.session-secret
    key: secret
    length: 64
    destinations: [backstage/generated/session-secret]
# Environment-specific additions, so the list above does not have to be restated
extraSecrets: []

    Reading a generated value

    Read it where the apps read it, in OpenBao, with the admin role (the token never reaches your shell):

    kubectl -n openbao create token openbao-admin --audience=openbao --duration=10m |
  kubectl -n openbao exec -i openbao-0 -c openbao -- \
    sh -c 'export BAO_TOKEN=$(bao write -field=token auth/kubernetes/login role=admin jwt=-); bao kv get -field=<property> secret/<namespace>/generated/<name>; bao token revoke -self >/dev/null'

    For example -field=password secret/ntfy/generated/phone-password. Or read the Secret the app's own ExternalSecret writes in its namespace.

    Adding a destination

    A destination added to an existing entry would get a new value (the push writes a missing destination with what it generates). Copy the existing value there first, inside OpenBao's pod so it never reaches your terminal, and mark the copy as External Secrets' (it refuses to write a path without that mark later); then add the destination to values.yaml: the push finds it and leaves it. For ntfy.alerts-token gaining <namespace>/generated/ntfy:

    kubectl -n openbao create token openbao-admin --audience=openbao --duration=10m |
  kubectl -n openbao exec -i openbao-0 -c openbao -- \
    sh -c 'export BAO_TOKEN=$(bao write -field=token auth/kubernetes/login role=admin jwt=-) &&
      bao kv get -field=token secret/ntfy/generated/alerts-token | bao kv put secret/<namespace>/generated/ntfy token=- &&
      bao kv metadata put -custom-metadata=managed-by=external-secrets secret/<namespace>/generated/ntfy;
      bao token revoke -self >/dev/null'

    Rotating

    lab secrets rotate <name> replaces any secret, generated or not, by its own method; a daily CronJob rotates the ones with a period (Rotating secrets). Kanidm OAuth2 client secrets are generated by the kaniop operator instead, as <client>-kanidm-oauth2-credentials in the client's namespace.

    Forgejo's deploy tokens and org ci's bot

    lab infra forgejo sync writes two records with the admin role: secret/forgejo/deploy (user deploy's token, which lab infra forgejo push uses) and secret/argocd/forgejo (user argocd's read-only token, which the ExternalSecret argocd/argocd-repo-forgejo reads). Running sync again keeps a token Forgejo still accepts and replaces one it does not (for example after Forgejo's data was lost), then refreshes Argo CD's credential.

    It also keeps ci-bot's token in secret/ci/forgejo-token (the golden path's clones and commit statuses), and records in secret/ci/forgejo-webhook the hash of the webhook header it gave org ci's hook, whose secret is the generated secret/ci/generated/webhook (In-cluster CI).

    Secrets from OpenTofu

    The unit infra/<env>/secrets (infra/_modules/secrets) writes one Secret per OpenBao path into namespace infra-secrets (<namespace>.<name>, one key per property) on every just infra deploy … (the sandbox's in just dev). platform/infra-secrets pushes each entry of its values.yaml to secret/<namespace>/<name> with updatePolicy: Replace: OpenTofu is the source, a changed value replaces OpenBao's within an hour, a lost one comes back.

    OpenBao path Source
    cert-manager/cloudflare, external-dns/cloudflare, cloudflared/cloudflare infra/production/cloudflare's output secrets (production)
    wireguard/private-key generated by the unit (wireguard_asymmetric_key); peers need terragrunt output wireguard_public_key in infra/<env>/secrets

    Tailscale's auth key (tailscale/auth-key) comes from Headscale in step 13. OpenTofu's Cloudflare login (cf auth login) never reaches the cluster.

    • Adding one: produce it in OpenTofu (an input of the unit, or a resource in the module), add its path and properties to platform/infra-secrets/values.yaml (and values-dev.yaml if the sandbox has it), and read it from its namespace. scripts/check-secret-stores refuses a push nobody reads.
    • Rotating one: change it in OpenTofu (for a Cloudflare token, terragrunt apply -replace=cloudflare_account_token.cert_manager in infra/production/cloudflare), run just infra deploy production, then kubectl -n infra-secrets annotate pushsecret <namespace>.<name> force-sync=$(date +%s) --overwrite or wait an hour, and restart the consumer.
    • Removing one: delete its entry, then its OpenBao value with the admin role (bao kv metadata delete …).
