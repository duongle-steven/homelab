    Deployment

    Open the development shell if you haven't already:

    nix develop

    The nodes, the first time

    infra/production/metal installs the machines of infra/production/metal/hosts.json the first time (nixie wakes them by Wake-on-LAN, boots them from the network and installs each with nixos-anywhere; PXE boot), joins them into one k3s cluster (lab cluster enroll), writes infra/production/kubeconfig.yaml, then upgrades nodes already installed in place, one at a time (lab cluster upgrade). Before the first run:

    1. Make production's own SSH key, with a passphrase, and load it; its public half goes in infra/production/metal/authorized_keys (commit it):

      ssh-keygen -t ed25519 -f ~/.ssh/homelab-production -C homelab-production
ssh-add ~/.ssh/homelab-production

    2. Under WSL (mirrored networking), let nixie's ports in: without these rules WSL sees no broadcast from the LAN. In an administrator PowerShell:

      New-NetFirewallHyperVRule -Name nixie-pxe-udp -DisplayName "nixie PXE (UDP)" -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -Protocol UDP -LocalPorts 67,69,4011
New-NetFirewallHyperVRule -Name nixie-pxe-tcp -DisplayName "nixie PXE (TCP)" -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -Protocol TCP -LocalPorts 80,5000

    3. Log in to Cloudflare for production's state (cf auth login, Account API Tokens enabled on its consent page).

    4. Switch the machines off: nixie wakes them.

    Then, with your machine's LAN address:

    cd infra/production/metal
HOMELAB_PXE_ADDRESS=192.168.0.224 terragrunt apply

    nixie writes each machine's machine_id_hash into hosts.json: commit it. A recorded machine is never installed again, and once every machine is recorded the hook neither asks for sudo nor needs HOMELAB_PXE_ADDRESS, so just infra deploy production runs it every time.

    To reinstall a node:

    1. Drain it and take it out of the cluster (kubectl drain <node> --ignore-daemonsets --delete-emptydir-data, then kubectl delete node <node>). Its etcd member leaves too: k3s removes a deleted server's member.
    2. Power it off: nixie wakes only machines that are off.
    3. Delete its machine_id_hash in hosts.json (the key, not just the value), commit.
    4. Forget its old host key: ssh-keygen -R <address>.
    5. Apply as for the first install, with the firewall rules and HOMELAB_PXE_ADDRESS.

    If the trust step stops with "no SSH from …", it prints ssh's own error: a changed host key needs step 4, and "Permission denied" a key missing from the agent (ssh-add ~/.ssh/homelab-production).

    Afterwards, remove the firewall rules:

    Remove-NetFirewallHyperVRule -Name nixie-pxe-udp, nixie-pxe-tcp

    The nodes' host keys were trusted on first contact (scripts/testbed-trust, for hosts.json's addresses only). To check one, compare ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the machine's console with ssh-keygen -lF <address> on yours.

    Then prove the nodes:

    just test e2e --env production --labels proof          # etcd, Secrets encrypted, seccomp
just test e2e --env production --focus NodesResolveQuickly
just test e2e --env production --labels scan           # kube-bench
scripts/node-fio <address>                              # once per node, before Ceph takes rook-data
just test e2e --env production --labels hardware-proof --verbose  # powers nodes off: never once real data is there

    --labels hardware-proof runs ProductionVIPMoves (a node powered off, woken by Wake-on-LAN) and ProductionPowerCut (you switch the power strip off and on). A routine just test e2e --env production never runs them, nor kube-bench.

    Measured on the hardware (2026-11-11)

    Three HP EliteDesk Minis (one 800 G4, two 800 G3), one 256 GB NVMe each, on a TP-Link Archer C64:

    • Install: the three in parallel in about 3 minutes, from nixie waking them to the record, over the laptop's Wi-Fi.
    • DNS through the Archer (DoH): an NXDOMAIN and an AAAA-less name in 110–140 ms on the nodes, 60–110 ms in a pod. Through 8.8.8.8 on UDP, the ISP modem's interception made the NXDOMAIN take 5 s.
    • fio, etcd's pattern (p99 fdatasync, budget 10 ms): homelab-2 and homelab-3 (Samsung MZAL8256HDJD) 5.1–5.7 ms; homelab-1 (SK hynix BC901) 10.7, 16.4 and 14.1 ms in three runs, over the budget every time. Its etcd's own WAL fsync averaged about 4 times the others'. A finding for step 12b-2.
    • fio on rook-data (173.5 GB per node): about 2.5 GiB/s sequential write, 3 GiB/s sequential read, 185–210k random 4k write IOPS and 260–277k random read IOPS on every node.
    • kube-bench: no finding outside .cluster-scan-accepted.yaml.
    • The VIP: the API answered through it 3–4 s after its holder powered off; Wake-on-LAN brought the node back in 2m43s (it tries the network first, finds no nixie, then boots its NVMe).
    • A power cut of the three nodes and the Archer together: every node booted by itself and the API answered at its VIP 1m11s after it went. Data written before a cut is checked in 12b-2, with Ceph.

    The rest

    Build the lab:

    just infra deploy production

    It runs the nodes' unit above (nothing to install once every machine is recorded), then the rest of the deploy below.

    Yes it's that simple!

    Note

    just infra deploy production deploys. It refuses anything but origin/master checked out without changes whose check checks passed and whose pull request's check sandbox passed (lab infra forgejo verify), applies infra/production, provisions Forgejo's org ops (lab infra forgejo sync: the users deploy and argocd, master's protection, their tokens in OpenBao), pushes the commit to ops/homelab (lab infra forgejo push), then applies the Argo CD bootstrap again. Argo CD does not manage itself, so a change to system/argocd reaches the cluster this way too. The first install is the same command: Argo CD reads the seed repository until its read-only token reads ops/homelab's master, then switches to Forgejo and never back (not even while Forgejo restarts). lab infra forgejo push alone deploys without touching the infrastructure. Only deploy can push to master, and nobody can force-push or delete it, Forgejo's site admins (forgejo_admin, homelab-admins) included; a site admin can still edit or remove the branch protection itself, a deliberate bypass the next lab infra forgejo sync (every just infra deploy production) undoes. Roll back with a revert through a pull request. --force applies the infrastructure only and deploys nothing (a state migration from another commit).
