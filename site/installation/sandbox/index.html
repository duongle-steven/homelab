    Development sandbox

    The sandbox is a local k3d cluster (one k3s server) for testing changes on the dev branch before they are merged into master.

    Prerequisites

    • Linux, or Windows with WSL 2 (NAT or mirrored networking). macOS does not work: the development shell includes Linux-only packages, and Docker runs in a VM there, so the host cannot reach the k3d network.
    • Docker and Nix (see development shell)
    • About 10 GiB of free RAM for Docker (the sandbox uses about 8 GiB, see resource usage)
    • Ports 80, 443 and 22 free on the host's 127.0.0.1

    Build

    git switch dev
nix develop
just dev

    just dev runs Terragrunt in infra/sandbox: the unit cluster creates the k3d cluster with k3s's own networking (Flannel, kube-proxy, ServiceLB) and the localhost proxy, the unit argocd bootstraps ArgoCD; then it runs the tests. State stays on your machine (.state/).

    The node pulls images through pull-through caches, one per registry (docker.io, ghcr.io, quay.io, registry.k8s.io, code.forgejo.org: k3d-homelab-cache-*, each with its own Docker volume). They are k3d registries outside the cluster, so just dev-clean and just dev-fresh keep them and a rebuilt sandbox downloads only what changed. A cached image expires a week after the cache first fetched it (registry:3 does not count later pulls), and the next build fetches it again; a new release is another tag, fetched on its first use, so after an upgrade the old one stays at most a week. An image from another registry, or one the cache fails to fetch, comes from its registry directly. Before it builds a cluster, just dev fills the caches one image at a time (scripts/warm-image-cache: every image the sandbox renders, plus k3s's, the operators' and the tests'; what a cache holds is skipped; --list prints them): the node pulls dozens of images at once, and on a slow link the cache's own request to the registry times out after 15 seconds (registry:3, not configurable), so the node would pull that image directly and the cache never get it. After the tests, scripts/warm-image-cache --node adds what the node holds and the caches miss, so the next build finds it. GitHub Actions runs without caches (HOMELAB_SANDBOX_CACHE=0: each runner starts empty). Empty one with k3d registry delete homelab-cache-docker-io (and docker volume rm homelab-cache-docker-io).

    Note

    The first build takes about 25 minutes. Running just dev again on an existing sandbox takes about a minute.

    Warning

    A sandbox built before step 8e (namespace global-secrets) needs just dev-fresh once: its OpenBao configured itself on first start with role writer bound to global-secrets, so generated-secrets cannot push to it.

    Explore

    just uses the sandbox kubeconfig automatically. For kubectl in your own shell, point it at the same file first:

    export KUBECONFIG=$PWD/infra/sandbox/kubeconfig.yaml  # from the repository root
    • https://argocd.127-0-0-1.nip.io (user admin, password: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d)
    • https://draw.127-0-0-1.nip.io
    • https://grafana.127-0-0-1.nip.io ("Sign in with Kanidm", or user admin with kubectl -n grafana get secret grafana-admin -o jsonpath='{.data.admin-password}' | base64 -d)
    • https://registry.127-0-0-1.nip.io (zot; log in with Kanidm, then create an API key under your user menu and docker login registry.127-0-0-1.nip.io -u <username> -p <key>)
    • https://git.127-0-0-1.nip.io (Forgejo; "Sign in with Kanidm", or user forgejo_admin with kubectl -n forgejo get secret forgejo-admin -o jsonpath='{.data.password}' | base64 -d; ops/homelab stays empty until TestForgejoDeploy runs lab infra forgejo sync and push; SSH on 127.0.0.1:22)
    • https://budget.127-0-0-1.nip.io (Actual Budget) and https://paperless.127-0-0-1.nip.io (only with just dev --apps paperless: paperless and OpenCloud are optional here, Sandbox tests): log in with Kanidm (paperless also has a local admin, password in OpenBao secret/paperless/generated/admin, property PAPERLESS_ADMIN_PASSWORD)
    • https://drive.127-0-0-1.nip.io (OpenCloud): log in with Kanidm and accept the consent page once
    • https://home.127-0-0-1.nip.io, https://drop.127-0-0-1.nip.io, https://speedtest.127-0-0-1.nip.io

    On Windows with WSL, open these from the Windows browser.

    Everything goes through the Gateway istio-system/gateway (Istio), which ServiceLB serves on the k3d node; a localhost proxy (homelab-dev-proxy, recreated by just dev) forwards 127.0.0.1:80/443/22 to it, because Windows cannot reach ports Docker publishes under WSL mirrored networking. The tests connect to the node directly. The Argo CD CLI works through it with --grpc-web.

    Certificates are issued by a local CA that is recreated with the cluster. To remove the browser warning, export it and import it into your trust store (on Windows: double-click homelab-dev-ca.crt → Install Certificate → Local Machine → Trusted Root Certification Authorities):

    kubectl -n cert-manager get secret homelab-dev-ca -o jsonpath='{.data.ca\.crt}' | base64 -d > homelab-dev-ca.crt

    Identity

    Kanidm (https://auth.127-0-0-1.nip.io) runs in the sandbox, and every app logs in to it directly with its own OAuth2 client. The test accounts and their groups:

    Test account Role group Access groups
    dev-admin homelab-admins homelab-budget, homelab-documents, homelab-files
    dev-editor homelab-editors homelab-documents, homelab-files
    dev-viewer homelab-users homelab-budget
    dev-outsider (none, refused) (none)

    The identity tests use the sandbox-only client smoke (platform/kanidm).

    The identity tests give each test account a password and TOTP the first time they run, and store them in the identity-test-credentials Secret in namespace kanidm:

    kubectl -n kanidm get secret identity-test-credentials -o jsonpath='{.data.dev-admin}' | base64 -d

    What each group may do:

    Group Grafana Argo CD zot Forgejo
    homelab-admins Admin, server admin admin read, push, delete site admin
    homelab-editors Editor view, sync, actions, logs, exec into apps/* read, push user
    homelab-users Viewer read-only read user

    Actual Budget admits only homelab-budget, paperless only homelab-documents (members of homelab-admins become paperless superusers), OpenCloud only homelab-files (members of homelab-admins get the Admin role, the others User).

    Argo CD and Grafana keep their local admin account, Forgejo its forgejo_admin; zot has a ci account for automation (password in OpenBao secret/zot/generated/ci; reading it).

    Use the totpSecret there in any authenticator app to log in by hand. Kanidm asks for the TOTP code before the password.

    If an account has credentials in Kanidm but none in that Secret (for example a run stopped mid-way), the tests cannot log in. Recreate the account so kaniop issues a new reset token:

    kubectl -n kanidm delete kanidmpersonaccount dev-admin  # ArgoCD recreates it
kubectl -n kanidm patch secret identity-test-credentials --type json -p '[{"op":"remove","path":"/data/dev-admin"}]'

    Group membership in the sandbox is declared in platform/kanidm/values-dev.yaml; people added by hand with scripts/onboard-user are removed from those groups on the next reconcile.

    Make changes

    Work on a feature branch created from dev, and run the basic checks before opening a pull request into dev:

    git switch dev && git pull
git switch -c feat/harness-the-sun
# ...edit, then for every changed chart or app file:
scripts/render-chart platform/kanidm
scripts/render-chart platform/kanidm dev
# the basic checks: the offline tests among them (test/e2e's specs need a cluster)
direnv exec . scripts/ci-check all
mkdocs build --strict
git commit -am "feat: harness the sun"
just dev   # pushes this commit to the branch sandbox and runs every sandbox test on it
git push -u origin feat/harness-the-sun   # then open a PR into dev

    ArgoCD in the sandbox syncs the GitHub branch sandbox. just dev force-pushes the commit you are on to it (so commit first) and runs the specs the branch's changes can affect (test/scopes.yaml; nothing when only docs or comments changed), so a branch is tested before its pull request (sandbox tests).

    Only the components listed in system/argocd/values-dev.yaml are synced: system and platform charts in the root ApplicationSet, apps in the apps ApplicationSet.

    • Apps are app-template values files, apps/<name>.yaml. The apps ApplicationSet pins the app-template version and passes the environment: write hosts as <host>.{{ .Values.global.baseDomain }}, and attach public apps to {{ .Values.global.publicGateway }} (the Cloudflare Tunnel Gateway in production, the LAN Gateway in the sandbox).
    • System and platform components are wrapper charts; one that needs sandbox-specific settings gets a values-dev.yaml next to its values.yaml, and what the sandbox shares with the testbed (the local CA, the tests' fixtures, no Telegram or Cloudflare) goes in values-local.yaml, loaded before it.

    Check how ArgoCD will render something with:

    scripts/render-chart apps/excalidraw.yaml dev
scripts/render-chart platform/kanidm dev

    What runs where

    The sandbox runs every component and app except what needs real hardware, the internet's side of the homelab or production's data. The authoritative lists are system/argocd/values-dev.yaml (sandbox), values-testbed.yaml (testbed) and values.yaml (production: every system/* and platform/*, every app).

    Sandbox Testbed Production
    Networking: Istio (Gateways, ambient mesh), egress, cert-manager yes Istio, cert-manager yes
    Storage csi-driver-host-path Ceph Ceph
    Addresses ServiceLB on the k3d node kube-vip kube-vip
    Security: Kyverno, Falco, Trivy Operator, the public scan yes no yes
    Observability: Prometheus, Alertmanager, Loki, OpenTelemetry, Tempo, Kiali, Grafana yes no yes
    Backups: Velero (to versitygw), CloudNativePG yes no yes (to R2)
    Identity and secrets: Kanidm, OpenBao, External Secrets, rotation yes no yes
    Git and CI: Forgejo, zot, Argo Workflows and Events, the golden path yes no yes
    Backstage (built from the checkout) yes no after its first release
    Apps: Actual Budget, Excalidraw, Homepage, Matrix, ntfy, PairDrop, Speedtest yes no yes
    Optional: paperless, OpenCloud when asked or changed no yes
    Cloudflare Tunnel, external-dns, Renovate, Jellyfin and its *arr apps, Tailscale, WireGuard, the blog no no yes

    "Changed" means the branch changes the app's file, not only its homelab: description.

    After a restart

    The sandbox survives a WSL or Docker restart: its containers start again (k3d cluster start homelab-dev if they do not) and keep their addresses. just dev makes each container's address on the k3d network static when it builds the cluster, because Docker otherwise gives a restarted container any free address, and k3s's etcd then refuses to start ("not a member of the etcd cluster": its member address is the old one). A sandbox built before that needs just dev-fresh once after such a restart; check with docker inspect -f '{{json .NetworkSettings.Networks}}' k3d-homelab-dev-server-0 (a static address shows in IPAMConfig).

    On WSL, a full C: drive crashes the whole VM (kernel panics with SIGBUS, reports in %LOCALAPPDATA%\Temp\wsl-crashes): the sandbox's disk grows inside WSL's virtual disk on C:, so keep about 30 GB free there during the suite.

    Never beside testbed: just dev refuses while testbed's VMs run (just testbed-stop), and both refuse with less than 30 GB free on C:.

    Clean up

    just dev-clean  # terragrunt run --all destroy in infra/sandbox: the cluster, the proxy and the kubeconfig (not the image caches)

    Differences from production

    • Certificates come from a local CA instead of Let's Encrypt
    • Only accessible from the host machine
    • No Renovate (production only)
    • Forgejo runs one PostgreSQL instance (CloudNativePG) instead of three; Argo CD syncs GitHub branch sandbox, not Forgejo (the tests push a commit with the checkout's tree to ops/homelab)
    • No Cloudflare Tunnel: excalidraw uses the LAN Gateway gateway instead of public
    • No kube-vip: ServiceLB serves the Gateway on the k3d node instead of a kube-vip address
