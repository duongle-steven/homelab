# Homelab (fork of khuedoan/homelab)

This fork diverges from upstream. It follows the direction of upstream's `nixos` rewrite (PR #197: NixOS + k3s nodes, Istio, OpenBao, Forgejo, `infra/` with OpenTofu/Terragrunt, `apps/*.yaml`) so its code can be reused; match that layout when a step restructures something.

## Roadmap

Each step changes one thing, with its own spec and plan in `docs/superpowers/`.

Step numbers are names, not the order. Order from here: 14d → 15a → 15b → 15c → 15e → 12a → 15d → 15f → 12b → 15g; 13 (needs production) and 14b fit in when convenient.

## Rules

- Use the latest stable release of every tool, chart and container image, pinned exactly (no `latest`; pin a digest when an image has no version tags). The versions in this repo are not a reference; check upstream when touching something. Hold a version back only for a compatibility constraint, and say which one next to the pin.
- Settings that depend on where the homelab runs (domain, time zone, seed repository, VIPs, router) live only in `infra/<env>/cluster/config.json` (upstream `nixos`'s format plus `service_vips`); Argo CD passes them to every chart and app as `global.baseDomain`, `global.timezone`, `global.seedRepository` and `global.addresses.*` (`scripts/env-values` does the same offline, and so does the bootstrap). Never name a global `domain` or `network`: argo-cd and Istio own those. Charts and app files hold no IP address or domain; a subchart that does not template a value gets it from a wrapper template (Argo CD's OIDC issuer Secret, Forgejo's `app.ini` section, zot's config): `scripts/check-env-config` checks it.
- Branches: create feature branches from `dev` and open PRs into `dev`; `dev` is merged into `master` through periodic PRs. Never commit straight to `dev` or `master` (the ruleset enforces it).
- The sandbox syncs the commit `make dev` pushes (GitHub branch `sandbox`). On a feature branch run the basic checks: `scripts/ci-check all` in the dev shell (`direnv exec .`): it renders every chart and app file the branch changes (`lab test charts`), runs `go vet` and the offline tests in `test/` (the state tests run `terragrunt` and `tofu`; the other tests need a cluster), `mkdocs build --strict`, the four `scripts/check-*`, `make -C infra check`, `make -C cli test check`, `scripts/lint` (yamllint, shellcheck, actionlint) and the detection checks `leaks`, `iac` and `images` (`docs/how-to-guides/ci.md`); GitHub Actions runs the same checks on every pull request (`docs/how-to-guides/ci.md`), and the ruleset `protect-dev-master` lets only pull requests whose `checks` passed reach `dev` and `master`; then commit and run `make dev`: it runs the sandbox tests the branch's changes can affect (`test/scopes.yaml`, `lab test scope --base origin/dev`), prints that there is nothing to test when every change is skipped, and otherwise force-pushes the commit to GitHub branch `sandbox` and runs them; its last run before the PR covers the whole branch. Label your own pull request `sandbox` only when it changes what the local sandbox cannot prove (the first install, CI). After the merge, a push to `dev` runs only the basic checks (`checks`): the workflow `sandbox` runs on demand (`gh workflow run sandbox.yaml --ref dev`). GitHub disables a fork's workflows now and then: no run starts, and the repository's Actions tab offers to re-enable them (`docs/how-to-guides/ci.md`). A `dev` → `master` PR runs the whole suite in a fresh sandbox, and the ruleset `protect-master-sandbox` requires it (its check `sandbox`, reported only by `sandbox-release` and, for a PR retargeted to `master`, `sandbox-retarget`: no other job may be named `sandbox`; `make dev-fresh` does the same locally). `make dev tests='<regex>'` runs exactly those tests. A new component gets its entry in `test/scopes.yaml` in the same PR (`make -C cli check` fails otherwise; until then it runs everything). If `dev` breaks, fix it with a new PR right away.
- Every PersistentVolumeClaim a chart or app renders carries the label `homelab/backup`: `daily` (off-site every day), `manual` (off-site only through `lab backup push`) or `none`, matching `EXPECTED` in `scripts/check-backup-groups` (a chart that cannot label its claim goes in `UNLABELLED` with the reason; Velero never backs it up).
- Every workload sets its securityContext (RuntimeDefault seccomp, no privilege escalation, non-root when the image allows) or carries a `PolicyException` with its reason (`docs/how-to-guides/policy.md`); `scripts/ci-check policy` fails otherwise, and a workload that breaks Pod Security baseline needs its namespace `privileged` in Argo CD's `templatePatch`.
- Every secret the repository makes has an entry in `cli/internal/rotate/catalog.yaml` (`lab secrets check`, run by `scripts/ci-check rotation-catalog`, fails otherwise; it also keeps `platform/secrets-rotation`'s readers and OpenBao's policy `rotator` in step with the scheduled entries): add it in the same change, with its method, class and reason (`docs/how-to-guides/secrets-rotation.md`).
- Review minors left open are tracked in `docs/superpowers/deferred-minors.md` (source PR, the step that handles them): a PR adds the minors it defers and removes the lines it fixes.
- Sandbox config lives next to production config and is selected with `env=dev`. Never fork config into a separate branch or directory.

## Sandbox

- `make dev` builds it (the tests of `test/scopes.yaml`'s selection; `scope=full` for all, `tests='<regex>'` for some; paperless and OpenCloud only when their app file changes or `apps=<names>|all` asks; `docs/how-to-guides/sandbox-tests.md`), `make dev-fresh` rebuilds it from scratch and runs everything, `make dev-clean` removes it; all three run only from the main checkout (the sandbox's state is its `.state/`; `make` refuses a git worktree). The selector `lab` runs with `go run` from `cli/` (Go module `github.com/duongle-steven/homelab/cli`, upstream `nixos`'s layout; its other commands come with the CLI step). Pages: `https://<app>.127-0-0-1.nip.io`.
- ArgoCD in the sandbox syncs `github.com/duongle-steven/homelab` branch `sandbox`, which `make dev` force-pushes to the current commit (it refuses uncommitted changes) and then refreshes; nothing merges from `sandbox`.
- Components synced in the sandbox are listed in `system/argocd/values-dev.yaml` (the `root` and `apps` ApplicationSets). Argo CD does not manage itself (upstream `nixos`'s model): `infra/_modules/argocd` applies `system/argocd` (Argo CD and both ApplicationSets) whenever it changes, and `system/argocd-config` (its Kanidm client and `argocd-repo-forgejo`, which need other components' CRDs) is synced by Argo CD. `root` keeps the resources of a directory it drops (`preserveResourcesOnDeletion`): delete them by hand. `make dev revision=<sha>` syncs that commit (it must be HEAD; uncommitted changes are refused here too) without pushing branch `sandbox` (`set-revision.sh`; GitHub Actions, `docs/how-to-guides/ci.md`), and `HOMELAB_SANDBOX_PROXY=0` drops the localhost proxy.
- Apps are app-template values files `apps/<name>.yaml`, deployed by the ApplicationSet `apps`, which pins app-template (in its source in `system/argocd/values.yaml`, restated in `values-dev.yaml` and `values-seed.yaml` because Helm replaces lists; so are both ApplicationSets' generators, the matrix that reads `infra/<env>/cluster/config.json`, which `scripts/check-env-config` checks) and passes `global.baseDomain` and `global.publicGateway` (`public` in production, `gateway` in the sandbox). Write hosts as `<host>.{{ .Values.global.baseDomain }}`. `apps/matrix/` is the only app chart.
- A system or platform component that needs different settings in the sandbox gets a `values-dev.yaml` next to its `values.yaml`. It is loaded only in the sandbox.
- Helm merges values files but cannot delete a key set in `values.yaml` (`null` only removes chart defaults); override with an inert value instead.
- `scripts/render-chart <dir|apps/<name>.yaml> [dev]` renders a component or app the way ArgoCD does.
- `make dev` and `make dev-clean` run Terragrunt in `infra/sandbox` (units `cluster`: `infra/_modules/k3d`, `openbao` (OpenBao's unseal key), `secrets` (OpenTofu's secrets into namespace `infra-secrets`; the sandbox has only the WireGuard key) and `argocd`: `infra/_modules/argocd`, which renders `system/argocd` and applies it again whenever its files, the revision or the cluster change; production's `infra/production/argocd` does the same, picking `values-seed.yaml` until Argo CD's token reads `ops/homelab`'s `master`). After deleting the k3d cluster by hand, run `make dev-clean` before `make dev` (Terragrunt does not notice). The sandbox's state is local in `.state/sandbox/` and production's is on R2 through its S3 API with a lock (`homelab-production-tfstate`, credentials from `lab` and `cf auth login` with Account API Tokens enabled), both encrypted with `HOMELAB_STATE_PASSPHRASE` (`~/.config/homelab/state.env`; rotate with `scripts/rotate-state-passphrase`; a state written before encryption needs one run with `HOMELAB_STATE_MIGRATE=1`); kubeconfigs are `infra/<env>/kubeconfig.yaml`.
- k3d cluster `homelab-dev` (one k3s server, `infra/_modules/k3d/k3d.yaml`; k3s's packaged Gateway API CRDs are disabled, the module installs the latest). ServiceLB serves the Gateway `istio-system/gateway` on the node; a localhost proxy (module `k3d`, recreated when the node address changes) forwards `127.0.0.1:80/443/22` there for the browser and SSH, and the tests dial the node IP (`docker inspect`). k3d's own port publishing is not used: Windows cannot reach it under WSL mirrored networking.
- The k3d node pulls through pull-through caches, one per registry (`infra/_modules/k3d`: k3d registries `homelab-cache-*` with their own volumes, `registries.yaml` mirrors with direct fallback; `make dev` fills them one image at a time with `scripts/warm-image-cache` before it builds a cluster, since a cache's upstream request times out after 15 seconds on a busy link, and after the tests adds what the node pulled without them (`--node`); an image expires a week after its first fetch; off in GitHub Actions, `HOMELAB_SANDBOX_CACHE=0`), which outlive the cluster: `make dev-fresh` downloads only what changed (`docs/installation/sandbox.md`).
- Volumes come from csi-driver-host-path (`system/csi-hostpath`, sandbox only, its default StorageClass; k3s's local-path is disabled) so the sandbox has CSI snapshots like Ceph: Velero's data mover and the hourly local snapshots run there as in production, with an S3 server (versitygw, `system/velero/values-dev.yaml`) standing in for R2. Velero's resources are named in full (`backups.velero.io`): CloudNativePG also serves a kind `Backup`.
- Certificates come from a local CA (`homelab-dev-ca` in namespace `cert-manager`), issued under the production issuer name `letsencrypt-prod`.
- Identity config is in git: groups and OAuth2 clients are kaniop resources. Every app has its own `KanidmOAuth2Client` in its own namespace (a chart's `templates/kanidm-client.yaml`, or `rawResources.kanidm-client` in an app file); add the namespace to `oauth2ClientNamespaces` in `platform/kanidm/values.yaml`. Apps read the kaniop Secret `<client>-kanidm-oauth2-credentials` (`CLIENT_SECRET`); Kanidm requires PKCE. People are created with `scripts/onboard-user`; never put personal data in the repo. Production `KanidmGroup`s must not set `members` (it replaces the whole membership).
- Kiali runs in the sandbox (`https://kiali.127-0-0-1.nip.io/kiali`, `docs/how-to-guides/kiali.md`), and so do the PodMonitors on Istio (`system/istio-system/templates/pod-monitors.yaml`) that feed it and Grafana.
- Loki and Alloy run in the sandbox (`system/loki`; a 2Gi PVC and 7 days in `values-dev.yaml`), and Grafana's Loki data source (uid `loki`) with them.
- In the sandbox, the ConfigMap `kube-system/coredns-custom` (from `system/istio-system`) makes k3s's CoreDNS rewrite `*.127-0-0-1.nip.io` to `gateway-istio.istio-system` so pods can reach Kanidm.
- The scheduled rotation (`platform/secrets-rotation`) runs in the sandbox on lab's image built from the checkout (`scripts/build-lab-image`, run by `make dev`); `TestRotation` (alone, after `TestBackupRestore`, `TestNodeRestart` and `TestNodePowerCut`: it restarts most apps) rotates one entry per method, `--all` from a script, and a due entry through the CronJob; Woodpecker's admin there includes `dev-admin`, so the test mints the token lab uses. A sandbox built before 11b needs `make dev-fresh` once (OpenBao gets its role `rotator` only at first start).
- Kanidm has a sandbox-only client `smoke` used by the identity tests (`make dev` runs `Smoke|Identity|SSO|Gateway|Forgejo|Mesh|Monitoring|Egress|Secrets|Ntfy|Logs|Woodpecker|Policy`, then `TestBackupRestore`, `TestNodeRestart`, `TestNodePowerCut` and `TestRotation` alone: the first restores the whole sandbox from a backup, the second restarts the node, the third kills and starts it, the fourth rotates secrets and restarts their readers). Admin tools (Grafana, Argo CD, zot, Forgejo) get short role group names in the claim `homelab_groups` from their client's `claimMap` and match `homelab-admins|editors|users`. Apps with personal data admit only an access group through `scopeMap`: `homelab-budget` (Actual Budget), `homelab-documents` (paperless; `homelab-admins` become superusers; a start script in `apps/paperless.yaml` gives the paperless group `homelab-documents` its permissions, and Kanidm groups replace paperless groups at each login), `homelab-files` (OpenCloud, public client `opencloud`; its `proxy.yaml` ConfigMap maps the claim `homelab_groups` to roles, `homelab-admins` → Admin, others → User; OpenCloud reads the claim from Kanidm's userinfo, not the access token).
- Apps trust the sandbox CA through the ConfigMap `homelab-dev-ca` (key `ca.crt`), which trust-manager copies into every namespace (sandbox only): Go apps (Grafana, Argo CD, zot, Forgejo) through `SSL_CERT_DIR` in `values-dev.yaml` (OpenCloud in its app file, only when `global.devCA` is set); app files mount it as an optional volume and set `NODE_EXTRA_CA_CERTS`/`REQUESTS_CA_BUNDLE` only when the `apps` parameter `global.devCA` is set.
- Apps publish `HTTPRoute`s (Forgejo also a `TCPRoute` for SSH) on `istio-system/gateway` (LAN) or `istio-system/public` (Cloudflare Tunnel), served by Istio (`system/istio-system`, like upstream); there are no `Ingress` objects. `scripts/render-chart` renders Gateway API kinds as `v1`, like ArgoCD.
- Every namespace Argo CD manages joins Istio's ambient mesh with strict mTLS (label from the shared `managedNamespaceMetadata`; `istio-system` and `rook-ceph` get `none` from the `root` `templatePatch`; `kube-system` is not managed). Pods the API server calls (webhooks) must carry the pod label `istio.io/dataplane-mode: none`; a chart's own NetworkPolicies must let TCP 15008 (ztunnel's HBONE port) in, as `templates/allow-hbone.yaml` in `system/argocd` and `apps/matrix` does; `scripts/check-mesh-policies` checks both in every chart. Inside the mesh nothing is reachable unless allowed (`deny-all` in `istio-system`; the Gateways keep `allow-gateways`): every meshed namespace needs an `AuthorizationPolicy` `allow` (same namespace, its Gateway on the route pod ports, Prometheus on metrics, named callers; Argo CD's lives in `system/istio-system`, in the same sync as `deny-all`, because the bootstrap (`infra/_modules/argocd`) applies the argocd chart before Istio's CRDs exist), and pods outside the mesh need a NetworkPolicy opening only their ports; add in-cluster calls the renders cannot show to `EXTRA` in `scripts/check-mesh-policies`. Istio's `k3s` platform profile serves the k3d sandbox too (its `k3d` profile has the wrong CNI path).
- A node restart can leave the mesh deadlocked: pods recreated before the node's ztunnel connects fail istio-cni's 5-second `cmdAdd`, containerd tears their sandboxes down, istio-cni's snapshot keeps the dead network namespaces and ztunnel retries them forever (`docs/superpowers/specs/2026-10-18-mesh-node-restart-design.md`). Two settings break it: `cni.ambient.ipv6: false` halves istio-cni's work per pod so pods fit under the 5 s again (pods only get IPv4; remove it if the cluster becomes dual-stack), and the CronJob `istio-system/istio-cni-watchdog` (`files/cni-watchdog.sh`) deletes a node's istio-cni pod when that node's ztunnel has run 180 s without becoming Ready, which clears the dead namespaces. `TestNodeRestart` proves the sandbox recovers (5 to 14 minutes measured; it allows 20). `cni.istioOwnedCNIConfig` stays on: k3s rewrites `10-flannel.conflist` at every start. `global.nativeNftables` crash-loops istio-cni on k3s in 1.31 (istio/istio#61078).
- Egress is denied by default (`system/egress`, rendered into every Application's namespace except `istio-system` and `rook-ceph`): pods reach the cluster, the API server (node network, port 6443) and the Gateway. A component or app that calls the internet adds its namespace and ports to `system/egress/values.yaml` (never `external-secrets`: ESO's controller reads every Secret, so a token from outside is minted in its user's namespace, as Renovate's is; `docs/reference/architecture/networking.md`) (`scripts/check-env-config` checks the wiring and the table). The sandbox's Docker network is fixed (`172.28.0.0/16`, `infra/_modules/k3d/k3d.yaml`) and named in `infra/sandbox/cluster/config.json`; if `make dev` cannot create it, another Docker network holds that range (`docker network ls`).
- Secrets live in OpenBao (`platform/openbao`): a component's `ExternalSecret`s read `SecretStore` `openbao` (rendered in every namespace by `system/secret-store`) with keys under its own namespace (`<namespace>/<name>`); generated secrets are pushed under `<namespace>/generated/`, the only paths OpenBao's `writer` role reaches, and a value two namespaces need is pushed to both branches (`destinations` in `platform/generated-secrets/values.yaml`, whose namespace holds only generators and PushSecrets: read a generated value from OpenBao, never from a copy; a sandbox built before 8e needs `make dev-fresh` once, its OpenBao binding `writer` to `global-secrets`); OpenTofu's secrets (`infra/<env>/secrets`) are Secrets in namespace `infra-secrets` that `platform/infra-secrets` pushes anywhere except `generated/` (role `infra`, `updatePolicy: Replace`); OpenBao's roles accept only tokens with audience `openbao`; `scripts/check-secret-stores` checks the stores and keys. OpenBao configures itself only on first start (its `initialize` stanzas): change a running one with the admin role (`docs/concepts/secrets-management.md`). Its unseal key comes from the OpenTofu unit `infra/<env>/openbao`.
- Forgejo (`platform/forgejo`) runs on PostgreSQL (CloudNativePG `forgejo-db`, `platform/cloudnative-pg`: three instances in production, one in the sandbox; a sandbox built before 11a needs `make dev-fresh` once: its `forgejo-data` holds repositories its new database does not know, and StatefulSets' claim templates gained the label `homelab/backup`, which Kubernetes does not change in place); `lab infra forgejo sync` creates an empty `ops/homelab` and `lab infra forgejo push` deploys to it (`make infra env=production`); production Argo CD syncs from there. In the sandbox it stays empty until `TestForgejoDeploy` runs both (the sandbox push is a commit with HEAD's tree on top of what Forgejo holds, so rebased branches still fast-forward). The Forgejo chart keeps Gitea's names for its own keys (`gitea:`, `configure-gitea`); everything else is named `forgejo`.
- The first sync on a fresh cluster takes about 20 minutes: some apps wait for CRDs (ServiceMonitor, ESO, kaniop, Istio's AuthorizationPolicy, cert-manager) and admission webhooks, then ArgoCD retries (in the sandbox from 30 s, doubling to at most 4 minutes, 18 tries, about an hour: `values-dev.yaml`; production keeps 1 to 16 minutes, 10 tries). These waits form a cycle (cert-manager ↔ istio-system ↔ monitoring-system), so only the resources in it (cert-manager's `allow` and ServiceMonitor, istio-system's Certificate and PodMonitors, monitoring-system's `allow`) carry `argocd.argoproj.io/sync-options: SkipDryRunOnMissingResource=true`: their sync applies the rest and retries them. So does every `PolicyException`: its CRD comes from `system/kyverno`, which needs Istio's (istio-system holds two exceptions: a cycle on a fresh cluster). Never set it for every Application: an app then applies part of itself, and a workload waiting for a Secret whose ExternalSecret failed keeps the sync running forever (zot did; Argo CD does not retry a sync it cut off). ESO's validating webhooks are `failurePolicy: Ignore` for the same reason: apps sync before the webhook has an endpoint, and a refused `ExternalSecret` left Argo CD waiting forever for its workload (zot, Woodpecker).

## Ideas (not planned)

- `cli/` exists with `lab test scope` and upstream's `lab infra state ensure|credentials`; grow it into a Go CLI like upstream `nixos`'s `lab` (`cli/`: cobra, the Cloudflare, OpenBao, Forgejo and Kubernetes SDKs, tests) replacing the shell scripts (`cloudflare-credentials`, `rotate-state-passphrase`, `onboard-user`) once they grow or get hard to test; port upstream's commands where they match.
- Progressive delivery with Argo Rollouts and Istio (already serving the Gateways and the mesh) splitting traffic by weight: canary or blue-green for stateless apps with two or more replicas (blog, homepage). Today Argo CD applies plain updates: app-template's default `Recreate` (most apps have one replica on a `ReadWriteOnce` PVC), `RollingUpdate` in upstream charts; rollback is a git revert.
- An external dead man's switch (e.g. healthchecks.io) for the Watchdog: ntfy's delayed message cannot fire when ntfy, the Tunnel or the cluster is down (Telegram, 11b, covers only ntfy being down); pause the check before switching the homelab off on purpose (healthchecks.io's API, e.g. from a shutdown command).
- A NAS (e.g. TrueNAS on ZFS) beside Ceph, which keeps the live data and its HA: a second backup copy in the house (Velero's second location, on S3 such as Garage; R2 stays the off-site copy, 3-2-1) for faster restores, and bulk storage for large data that needs no HA (Jellyfin's media over NFS: Ceph's two replicas double its disks); databases stay on Ceph. Worth it once bulk data outgrows the nodes' disks or restores from R2 get too slow.
- Leak detection: GitHub secret scanning and push protection, gitleaks in the basic checks, alerts from OpenBao's, Cloudflare's and GitHub's audit logs; a suspected leak is then `lab secrets rotate <name>`.
- Tracing: an OpenTelemetry Collector and Grafana Tempo, with OTLP from the tools that emit it (Grafana, Loki, Argo CD, Kanidm, the Gateways' Envoy); in ambient mode ztunnel makes no spans (L4 only), so traces inside the mesh need waypoints, and the everyday apps emit none: worth it once there are apps of our own or a latency to chase.
