# Homelab (fork of khuedoan/homelab)

This fork diverges from upstream. It follows the direction of upstream's `nixos` rewrite (PR #197: NixOS + k3s nodes, Istio, OpenBao, Forgejo, `infra/` with OpenTofu/Terragrunt, `apps/*.yaml`) so its code can be reused; match that layout when a step restructures something.

## Roadmap

Each step changes one thing, with its own spec and plan in `docs/superpowers/`.

## Rules

- Use the latest stable release of every tool, chart and container image, pinned exactly (no `latest`; pin a digest when an image has no version tags). The versions in this repo are not a reference; check upstream when touching something. Hold a version back only for a compatibility constraint, and say which one next to the pin.
- Settings that depend on where the homelab runs (domain, time zone, seed repository, VIPs, router) live only in `infra/<env>/cluster/config.json` (upstream `nixos`'s format plus `service_vips`); Argo CD passes them to every chart and app as `global.baseDomain`, `global.timezone`, `global.seedRepository` and `global.addresses.*` (`scripts/env-values` does the same offline, and so does the bootstrap). Never name a global `domain` or `network`: argo-cd and Istio own those. Charts and app files hold no IP address or domain; a subchart that does not template a value gets it from a wrapper template (Argo CD's OIDC issuer Secret, Forgejo's `app.ini` section, zot's config): `scripts/check-env-config` checks it.
- Branches: create feature branches from `dev` and open PRs into `dev`; `dev` is merged into `master` through periodic PRs. Never commit straight to `dev` or `master` (the ruleset enforces it).
- The sandbox syncs the commit `make dev` pushes (GitHub branch `sandbox`). On a feature branch run the basic checks: `scripts/ci-check all` in the dev shell (`direnv exec .`): it renders every chart and app file the branch changes (`lab test charts`), runs `go vet` and the offline tests in `test/` (the state tests run `terragrunt` and `tofu`; the other tests need a cluster), `mkdocs build --strict`, the four `scripts/check-*`, `make -C infra check`, `make -C cli test check` and `scripts/lint` (yamllint, shellcheck, actionlint); GitHub Actions runs the same checks on every pull request (`docs/how-to-guides/ci.md`), and the ruleset `protect-dev-master` lets only pull requests whose `checks` passed reach `dev` and `master`; then commit and run `make dev`: it runs the sandbox tests the branch's changes can affect (`test/scopes.yaml`, `lab test scope --base origin/dev`), prints that there is nothing to test when every change is skipped, and otherwise force-pushes the commit to GitHub branch `sandbox` and runs them; its last run before the PR covers the whole branch. Label your own pull request `sandbox` only when it changes what the local sandbox cannot prove (the first install, CI). After the merge, the workflow `sandbox` runs the whole suite on `dev` in a fresh sandbox (a newer push cancels an older run; it skips when every change since the last push that passed was skipped): check that run. A `dev` → `master` PR runs the whole suite in a fresh sandbox, and the ruleset `protect-master-sandbox` requires it (its check `sandbox`, reported only by `sandbox-release` and, for a PR retargeted to `master`, `sandbox-retarget`: no other job may be named `sandbox`; `make dev-fresh` does the same locally). `make dev tests='<regex>'` runs exactly those tests. A new component gets its entry in `test/scopes.yaml` in the same PR (`make -C cli check` fails otherwise; until then it runs everything). If `dev` breaks, fix it with a new PR right away.
- Every PersistentVolumeClaim a chart or app renders carries the label `homelab/backup`: `daily` (off-site every day), `manual` (off-site only through `lab backup push`) or `none`, matching `EXPECTED` in `scripts/check-backup-groups` (a chart that cannot label its claim goes in `UNLABELLED` with the reason; Velero never backs it up).
- Review minors left open are tracked in `docs/superpowers/deferred-minors.md` (source PR, the step that handles them): a PR adds the minors it defers and removes the lines it fixes.
- Sandbox config lives next to production config and is selected with `env=dev`. Never fork config into a separate branch or directory.

## Sandbox

- `make dev` builds it (the tests of `test/scopes.yaml`'s selection; `scope=full` for all, `tests='<regex>'` for some; `docs/how-to-guides/sandbox-tests.md`), `make dev-fresh` rebuilds it from scratch and runs everything, `make dev-clean` removes it; all three run only from the main checkout (the sandbox's state is its `.state/`; `make` refuses a git worktree). The selector `lab` runs with `go run` from `cli/` (Go module `github.com/duongle-steven/homelab/cli`, upstream `nixos`'s layout; its other commands come with the CLI step). Pages: `https://<app>.127-0-0-1.nip.io`.
- ArgoCD in the sandbox syncs `github.com/duongle-steven/homelab` branch `sandbox`, which `make dev` force-pushes to the current commit (it refuses uncommitted changes) and then refreshes; nothing merges from `sandbox`.
- Components synced in the sandbox are listed in `system/argocd/values-dev.yaml` (the `root` and `apps` ApplicationSets). Argo CD does not manage itself (upstream `nixos`'s model): `infra/_modules/argocd` applies `system/argocd` (Argo CD and both ApplicationSets) whenever it changes, and `system/argocd-config` (its Kanidm client and `argocd-repo-forgejo`, which need other components' CRDs) is synced by Argo CD. `root` keeps the resources of a directory it drops (`preserveResourcesOnDeletion`): delete them by hand. `make dev revision=<sha>` syncs that commit (it must be HEAD; uncommitted changes are refused here too) without pushing branch `sandbox` (`set-revision.sh`; GitHub Actions, `docs/how-to-guides/ci.md`), and `HOMELAB_SANDBOX_PROXY=0` drops the localhost proxy.
- Apps are app-template values files `apps/<name>.yaml`, deployed by the ApplicationSet `apps`, which pins app-template (in its source in `system/argocd/values.yaml`, restated in `values-dev.yaml` and `values-seed.yaml` because Helm replaces lists; so are both ApplicationSets' generators, the matrix that reads `infra/<env>/cluster/config.json`, which `scripts/check-env-config` checks) and passes `global.baseDomain` and `global.publicGateway` (`public` in production, `gateway` in the sandbox). Write hosts as `<host>.{{ .Values.global.baseDomain }}`. `apps/matrix/` is the only app chart.
- A system or platform component that needs different settings in the sandbox gets a `values-dev.yaml` next to its `values.yaml`. It is loaded only in the sandbox.
- Helm merges values files but cannot delete a key set in `values.yaml` (`null` only removes chart defaults); override with an inert value instead.
- `scripts/render-chart <dir|apps/<name>.yaml> [dev]` renders a component or app the way ArgoCD does.
- `make dev` and `make dev-clean` run Terragrunt in `infra/sandbox` (units `cluster`: `infra/_modules/k3d`, `openbao` (OpenBao's unseal key), `secrets` (OpenTofu's secrets into namespace `infra-secrets`; the sandbox has only the WireGuard key) and `argocd`: `infra/_modules/argocd`, which renders `system/argocd` and applies it again whenever its files, the revision or the cluster change; production's `infra/production/argocd` does the same, picking `values-seed.yaml` until Argo CD's token reads `ops/homelab`'s `master`). After deleting the k3d cluster by hand, run `make dev-clean` before `make dev` (Terragrunt does not notice). The sandbox's state is local in `.state/sandbox/` and production's is on R2 through its S3 API with a lock (`homelab-production-tfstate`, credentials from `lab` and `cf auth login` with Account API Tokens enabled), both encrypted with `HOMELAB_STATE_PASSPHRASE` (`~/.config/homelab/state.env`; rotate with `scripts/rotate-state-passphrase`; a state written before encryption needs one run with `HOMELAB_STATE_MIGRATE=1`); kubeconfigs are `infra/<env>/kubeconfig.yaml`.
- k3d cluster `homelab-dev` (one k3s server, `infra/_modules/k3d/k3d.yaml`; k3s's packaged Gateway API CRDs are disabled, the module installs the latest). ServiceLB serves the Gateway `istio-system/gateway` on the node; a localhost proxy (module `k3d`, recreated when the node address changes) forwards `127.0.0.1:80/443/22` there for the browser and SSH, and the tests dial the node IP (`docker inspect`). k3d's own port publishing is not used: Windows cannot reach it under WSL mirrored networking.
- Volumes come from csi-driver-host-path (`system/csi-hostpath`, sandbox only, its default StorageClass; k3s's local-path is disabled) so the sandbox has CSI snapshots like Ceph: Velero's data mover and the hourly local snapshots run there as in production, with an S3 server (versitygw, `system/velero/values-dev.yaml`) standing in for R2. Velero's resources are named in full (`backups.velero.io`): CloudNativePG also serves a kind `Backup`.
- Certificates come from a local CA (`homelab-dev-ca` in namespace `cert-manager`), issued under the production issuer name `letsencrypt-prod`.
- Identity config is in git: groups and OAuth2 clients are kaniop resources. Every app has its own `KanidmOAuth2Client` in its own namespace (a chart's `templates/kanidm-client.yaml`, or `rawResources.kanidm-client` in an app file); add the namespace to `oauth2ClientNamespaces` in `platform/kanidm/values.yaml`. Apps read the kaniop Secret `<client>-kanidm-oauth2-credentials` (`CLIENT_SECRET`); Kanidm requires PKCE. People are created with `scripts/onboard-user`; never put personal data in the repo. Production `KanidmGroup`s must not set `members` (it replaces the whole membership).
- Loki and Alloy run in the sandbox (`system/loki`; a 2Gi PVC and 7 days in `values-dev.yaml`), and Grafana's Loki data source (uid `loki`) with them.
- In the sandbox, the ConfigMap `kube-system/coredns-custom` (from `system/istio-system`) makes k3s's CoreDNS rewrite `*.127-0-0-1.nip.io` to `gateway-istio.istio-system` so pods can reach Kanidm.
- Kanidm has a sandbox-only client `smoke` used by the identity tests (`make dev` runs `Smoke|Identity|SSO|Gateway|Forgejo|Mesh|Monitoring|Egress|Secrets|Ntfy|Logs|Woodpecker`, then `TestBackupRestore` and `TestNodeRestart` alone: the first restores the whole sandbox from a backup, the second restarts the node). Admin tools (Grafana, Argo CD, zot, Forgejo) get short role group names in the claim `homelab_groups` from their client's `claimMap` and match `homelab-admins|editors|users`. Apps with personal data admit only an access group through `scopeMap`: `homelab-budget` (Actual Budget), `homelab-documents` (paperless; `homelab-admins` become superusers; a start script in `apps/paperless.yaml` gives the paperless group `homelab-documents` its permissions, and Kanidm groups replace paperless groups at each login), `homelab-files` (OpenCloud, public client `opencloud`; its `proxy.yaml` ConfigMap maps the claim `homelab_groups` to roles, `homelab-admins` → Admin, others → User; OpenCloud reads the claim from Kanidm's userinfo, not the access token).
- Apps trust the sandbox CA through the ConfigMap `homelab-dev-ca` (key `ca.crt`), which trust-manager copies into every namespace (sandbox only): Go apps (Grafana, Argo CD, zot, Forgejo) through `SSL_CERT_DIR` in `values-dev.yaml` (OpenCloud in its app file, only when `global.devCA` is set); app files mount it as an optional volume and set `NODE_EXTRA_CA_CERTS`/`REQUESTS_CA_BUNDLE` only when the `apps` parameter `global.devCA` is set.
- Apps publish `HTTPRoute`s (Forgejo also a `TCPRoute` for SSH) on `istio-system/gateway` (LAN) or `istio-system/public` (Cloudflare Tunnel), served by Istio (`system/istio-system`, like upstream); there are no `Ingress` objects. `scripts/render-chart` renders Gateway API kinds as `v1`, like ArgoCD.
- Every namespace Argo CD manages joins Istio's ambient mesh with strict mTLS (label from the shared `managedNamespaceMetadata`; `istio-system` and `rook-ceph` get `none` from the `root` `templatePatch`; `kube-system` is not managed). Pods the API server calls (webhooks) must carry the pod label `istio.io/dataplane-mode: none`; a chart's own NetworkPolicies must let TCP 15008 (ztunnel's HBONE port) in, as `templates/allow-hbone.yaml` in `system/argocd` and `apps/matrix` does; `scripts/check-mesh-policies` checks both in every chart. Inside the mesh nothing is reachable unless allowed (`deny-all` in `istio-system`; the Gateways keep `allow-gateways`): every meshed namespace needs an `AuthorizationPolicy` `allow` (same namespace, its Gateway on the route pod ports, Prometheus on metrics, named callers; Argo CD's lives in `system/istio-system`, in the same sync as `deny-all`, because the bootstrap (`infra/_modules/argocd`) applies the argocd chart before Istio's CRDs exist), and pods outside the mesh need a NetworkPolicy opening only their ports; add in-cluster calls the renders cannot show to `EXTRA` in `scripts/check-mesh-policies`. Istio's `k3s` platform profile serves the k3d sandbox too (its `k3d` profile has the wrong CNI path).
- A node restart can leave the mesh deadlocked: pods recreated before the node's ztunnel connects fail istio-cni's 5-second `cmdAdd`, containerd tears their sandboxes down, istio-cni's snapshot keeps the dead network namespaces and ztunnel retries them forever (`docs/superpowers/specs/2026-10-18-mesh-node-restart-design.md`). Two settings break it: `cni.ambient.ipv6: false` halves istio-cni's work per pod so pods fit under the 5 s again (pods only get IPv4; remove it if the cluster becomes dual-stack), and the CronJob `istio-system/istio-cni-watchdog` (`files/cni-watchdog.sh`) deletes a node's istio-cni pod when that node's ztunnel has run 180 s without becoming Ready, which clears the dead namespaces. `TestNodeRestart` proves the sandbox recovers (5 to 14 minutes measured; it allows 20). `cni.istioOwnedCNIConfig` stays on: k3s rewrites `10-flannel.conflist` at every start. `global.nativeNftables` crash-loops istio-cni on k3s in 1.31 (istio/istio#61078).
- Egress is denied by default (`system/egress`, rendered into every Application's namespace except `istio-system` and `rook-ceph`): pods reach the cluster, the API server (node network, port 6443) and the Gateway. A component or app that calls the internet adds its namespace and ports to `system/egress/values.yaml` (never `external-secrets`: ESO's controller reads every Secret, so a token from outside is minted in its user's namespace, as Renovate's is; `docs/reference/architecture/networking.md`) (`scripts/check-env-config` checks the wiring and the table). The sandbox's Docker network is fixed (`172.28.0.0/16`, `infra/_modules/k3d/k3d.yaml`) and named in `infra/sandbox/cluster/config.json`; if `make dev` cannot create it, another Docker network holds that range (`docker network ls`).
- Secrets live in OpenBao (`platform/openbao`): a component's `ExternalSecret`s read `SecretStore` `openbao` (rendered in every namespace by `system/secret-store`) with keys under its own namespace (`<namespace>/<name>`); generated secrets are pushed under `<namespace>/generated/`, the only paths OpenBao's `writer` role reaches, and a value two namespaces need is pushed to both branches (`destinations` in `platform/generated-secrets/values.yaml`, whose namespace holds only generators and PushSecrets: read a generated value from OpenBao, never from a copy; a sandbox built before 8e needs `make dev-fresh` once, its OpenBao binding `writer` to `global-secrets`); OpenTofu's secrets (`infra/<env>/secrets`) are Secrets in namespace `infra-secrets` that `platform/infra-secrets` pushes anywhere except `generated/` (role `infra`, `updatePolicy: Replace`); OpenBao's roles accept only tokens with audience `openbao`; `scripts/check-secret-stores` checks the stores and keys. OpenBao configures itself only on first start (its `initialize` stanzas): change a running one with the admin role (`docs/concepts/secrets-management.md`). Its unseal key comes from the OpenTofu unit `infra/<env>/openbao`.
- Forgejo (`platform/forgejo`) runs on PostgreSQL (CloudNativePG `forgejo-db`, `platform/cloudnative-pg`: three instances in production, one in the sandbox; a sandbox built before 11a needs `make dev-fresh` once: its `forgejo-data` holds repositories its new database does not know, and StatefulSets' claim templates gained the label `homelab/backup`, which Kubernetes does not change in place); `lab infra forgejo sync` creates an empty `ops/homelab` and `lab infra forgejo push` deploys to it (`make infra env=production`); production Argo CD syncs from there. In the sandbox it stays empty until `TestForgejoDeploy` runs both (the sandbox push is a commit with HEAD's tree on top of what Forgejo holds, so rebased branches still fast-forward). The Forgejo chart keeps Gitea's names for its own keys (`gitea:`, `configure-gitea`); everything else is named `forgejo`.
- The first sync on a fresh cluster takes about 20 minutes: some apps wait for CRDs (ServiceMonitor, ESO, kaniop, Istio's AuthorizationPolicy, cert-manager) and admission webhooks, then ArgoCD retries. These waits form a cycle (cert-manager ↔ istio-system ↔ monitoring-system), so only the resources in it (cert-manager's `allow` and ServiceMonitor, istio-system's Certificate, monitoring-system's `allow`) carry `argocd.argoproj.io/sync-options: SkipDryRunOnMissingResource=true`: their sync applies the rest and retries them. Never set it for every Application: an app then applies part of itself, and a workload waiting for a Secret whose ExternalSecret failed keeps the sync running forever (zot did; Argo CD does not retry a sync it cut off). ESO's validating webhooks are `failurePolicy: Ignore` for the same reason: apps sync before the webhook has an endpoint, and a refused `ExternalSecret` left Argo CD waiting forever for its workload (zot, Woodpecker).

## Before the first production deploy (sub-project 3)

The sandbox runs Kubernetes 1.37 and only ever installs from scratch, so it does not prove these:

- k3s defaults (Flannel, kube-proxy, ServiceLB, network policy), the Gateway API CRDs through k3s's auto-deploy manifests (k3s's packaged ones disabled), kube-vip v1.2.4 serving class `kube-vip.io/kube-vip-class` and its addresses `192.168.0.2` (Gateway) and `192.168.0.3` (wireguard) were only rendered: the sandbox has no kube-vip. `metal/inventories/prod.yml` has the node addresses `192.168.0.11-13` but placeholder MAC addresses (`FILL-ME`), disks and interfaces: fill them in first.
- Major chart upgrades in sub-project 2 were only rendered, never run in production: app-template 2/3 → 5 (blog, jellyfin, ollama, paperless, cloudflared, and in step 4 tailscale and wireguard; PVC names kept with `suffix: data`), woodpecker 1 → 3, dendrite 0.13 → 0.14.
- App images jumped several majors (step 3) and only the sandbox apps ran: paperless-ngx 2 → 3 (consume script arguments and advanced DB settings changed), homepage 0.8 → 2 (`HOMEPAGE_ALLOWED_HOSTS` required; v2 adds optional homepage auth), Jellyseerr replaced by its successor Seerr (`ghcr.io/seerr-team/seerr`), jellyfin 10.8 → 10.11, ollama 0.1 → 0.40, redis 7 → 8.
- `infra/production/cloudflare` creates the Tunnel, its record and the DNS tokens; their secrets (its output `secrets`) reach the cluster through `infra/production/secrets` (`make infra env=production`, once Argo CD has created namespace `infra-secrets`) and OpenBao; the ExternalSecrets of cloudflared, cert-manager and external-dns were only rendered. OpenTofu's Cloudflare credentials come from `cf auth login` (enable Account API Tokens on the consent page). Its state is on R2.
- The public path is untested: Gateway `istio-system/public`, cloudflared `matchSNItoHost` to `public-istio.istio-system`, external-dns 1.23 with `gateway-httproute` and the `external-dns.kubernetes.io/` annotation prefix.
- k3s jumps 1.30 → 1.37; upgrade an existing cluster one minor at a time (Istio 1.31 supports Kubernetes 1.32–1.37).
- Charts with changed workload selectors cannot be upgraded in place: delete the Deployment once or sync with `Replace=true`. This covers every app-template 2/3 → 5 upgrade (excalidraw, actualbudget, blog, homepage, jellyfin, ollama, pairdrop, paperless, speedtest, cloudflared, tailscale, wireguard; selector `component` → `controller`). ollama's Deployment is also renamed `ollama` → `ollama-main` and only starts once the old pod releases the `ollama-data` volume. wireguard's Service gains `loadBalancerClass` (kube-vip), which Kubernetes never changes on an existing Service, not even with `Replace=true`: delete the Service once. Loki's StatefulSet `loki` (loki-stack → the `loki` chart, step 9) changes its selector and volume claims: delete it once (loki-stack kept no data) or sync with `Replace=true`; an existing Grafana that stored the Loki data source under another uid may need it deleted once so the provisioned `uid: loki` takes over.
- Set `infra/production/cluster/config.json` (domain `hoangduong.dev`, time zone, seed repository, addresses). Two settings stay outside it: `apps/matrix/values.yaml` names the domain (dendrite and element-web cannot take it from a global) and `system/kured/values.yaml`, `platform/renovate/values.yaml` and `metal/roles/pxe_server/defaults/main.yml` the time zone (kured's and Renovate's charts do not template it; the PXE role is Ansible).
- The production-only allows (Loki, Woodpecker and Forgejo's webhooks to it, Grafana to Alertmanager, Argo CD's repo server to Forgejo, CloudNativePG's operator to `forgejo-db`, Matrix) were only rendered.
- The ambient mesh on k3s, the CloudNativePG operator's opt-out (plus `PeerAuthentication` `forgejo-db-status`, port 8000 permissive, so the operator reaches the instances), the VPN routers' opt-out (wireguard, tailscale) and rook-ceph's exclusion were only rendered. istio-cni enrols running pods when their namespace gets the label and re-applies its rules when it restarts, so no pod restart is needed.
- Wireguard's peers (`apps/wireguard.yaml`) carry PLACEHOLDER public keys (random; nobody can connect): replace the server's (`terragrunt output -raw wireguard_public_key` in `infra/production/secrets`) and each device's before using the VPN, keeping their tunnel addresses.
- The control-plane scrape by node discovery ran only on the one-node sandbox.
- Egress (`system/egress`) ran only for the sandbox's namespaces: the internet table for production-only namespaces (cert-manager's ACME and DNS01, external-dns, cloudflared, the ntfy relay, renovate, woodpecker, ollama, matrix, jellyfin, tailscale, wireguard) and the Gateway VIP rule were only rendered. Applications now have several sources (component plus `system/egress`), and Argo CD keeps no rollback history for those: roll back with git.
- Production's Argo CD bootstrap through Terragrunt (`infra/production/argocd`, seed selection) was only planned against the sandbox; nodes still come from `make -C metal` (in `nix develop .#metal`, the shell with Ansible), which writes `infra/production/kubeconfig.yaml`.
- OpenCloud only ran in the sandbox. `opencloud-config` holds the secrets `opencloud init` generated and the internal LDAP (accounts, shares); losing it loses them (group `manual`: off-site only through `lab backup push opencloud`). The desktop and mobile apps need their own public Kanidm clients.
- Renovate (`platform/renovate`) only ran once on the sandbox, in dry-run (its token minted, Renovate logged in, the token revoked); its first real run (pull requests into `dev` labelled `sandbox`) follows the release that puts `renovate.json5` on `master`, the default branch Renovate reads it from; production's `infra-secrets` waits for `renovate/github-app` until the key is given (`docs/how-to-guides/renovate.md`).
- Woodpecker (`platform/woodpecker`) ran only in the sandbox with one agent: two agents, its server's PVC on rook-ceph, step pods' user namespaces on the NixOS k3s nodes and TLS from step pods to `git.` and `registry.` (the sandbox's pipeline skips verification) are unproven, and its org secrets are set by hand (`docs/how-to-guides/woodpecker.md`); wireguard reads `secret/wireguard/private-key` (written by `infra/production/secrets`); tailscale reads `secret/tailscale/auth-key`, which Headscale writes in step 13: production built before that leaves tailscale waiting for its Secret (or write a key with the admin role, `docs/getting-started/vpn-setup.md`).
- OpenBao (static seal, self-initialisation, raft on a PVC) only ran in the sandbox. Its data is backed up as an hourly raft snapshot (`openbao-snapshots`, off-site daily); its unseal key lives in production's encrypted state on R2 (`openbao/tfstate.json`): losing either loses every secret. Apply `infra/production/openbao` together with `argocd` (`make infra env=production`); the pod waits for the Secret.
- Loki and Alloy (`system/loki`) only ran in the sandbox: Loki's 10Gi PVC on rook-ceph, the 30-day retention's size and Alloy reading `/var/log/pods` on the NixOS k3s nodes are unproven.
- Node-restart recovery (the istio-cni watchdog, `cni.ambient.ipv6: false`, `istioOwnedCNIConfig`) only ran on the one-node sandbox, where every node restart deadlocks the mesh without the watchdog; istiod's two replicas spread over nodes were only rendered. Give k3s's CoreDNS two replicas on different nodes in step 12 (`kube-system` is outside Argo CD), so a rebooted node's ztunnel finds DNS and istiod at once. A power loss that restarts every node is unmeasured on real hardware.
- ntfy (`apps/ntfy.yaml`) only ran in the sandbox, without ntfy.sh: its public route (Tunnel, Gateway `public`, external-dns), `NTFY_UPSTREAM_BASE_URL` (iOS push) and egress 443 for `ntfy` were only rendered. Subscribe phones as `docs/how-to-guides/alerts.md` says.
- Backups (`system/velero`, `infra/production/backup`, `docs/how-to-guides/backup-and-restore.md`) ran only in the sandbox (csi-driver-host-path, versitygw): Ceph's snapshots and the space they take, Velero's data mover on Ceph (the class label `velero.io/csi-volumesnapshot-class`), R2 with its write-only token and the endpoint in the credentials file, egress 443 for `velero`, Matrix's volumes (moved to `apps/matrix/templates/volumes.yaml` under their old names) and its PostgreSQL's restore were only rendered. A whole-cluster restore in production was never run (in production Argo CD reads the restored Forgejo, and `lab` waits for Argo CD only after refreshing every ExternalSecret; run `make infra env=production` right after it, as the guide says). Run `lab backup enable` once after the first production deploy (every new cluster starts read-only; the alert `VeleroNoRecentBackup` fires until then), and keep the state passphrase: it guards the Kopia password and the R2 credentials.
- CloudNativePG ran only with one instance (the sandbox): `forgejo-db`'s three instances and their failover were only rendered.
- Argo CD's switch to `ops/homelab` on Forgejo (`values.yaml`, `infra/_modules/argocd/choose-values.sh`, repository Secret `argocd-repo-forgejo` with `argocd`'s read-only token) is only rendered: `make infra env=production` deploys in one command (`lab infra forgejo verify`, apply, `sync`, `push`, the bootstrap again), and the bootstrap switches once Argo CD's token reads `ops/homelab`'s `master` (never back, even while Forgejo restarts); the sandbox tests prove `sync`, `push`, the protection and that the credential reads the repository, not the switch.
- Argo CD has `exec.enabled: "true"` (needed for the editor role), so admins and editors can open terminals in pods.
- The Grafana chart now comes from `https://grafana-community.github.io/helm-charts`.
- zot refuses anonymous pulls: `apps/blog` (`registry.<domain>/blog`) needs pull credentials (a read-only htpasswd account plus an `imagePullSecret`) or an anonymous `read` policy for its repository.
- Forgejo does not start while Kanidm is unreachable: its init container registers the Kanidm login source at every start and needs Kanidm's discovery document. Argo CD syncs from Forgejo, so bring Kanidm back first after an outage.
- zot exits at start when Kanidm is unreachable (OIDC discovery), so a Kanidm outage plus a zot restart also stops `ci` and API-key pulls and pushes.
- The first person to log in to Actual Budget with OpenID becomes its server owner: add yourself to `homelab-budget` and log in first.
- Removing someone from Kanidm or a group does not revoke their zot API keys (zot keeps the groups from their last login); delete their keys in zot when offboarding; the same holds for their Woodpecker personal tokens and session: delete their Woodpecker user too.
- Argo CD editors may exec only into apps listed in `system/argocd/values.yaml` (`apps/*`); add new apps there.

## Ideas (not planned)

- `cli/` exists with `lab test scope` and upstream's `lab infra state ensure|credentials`; grow it into a Go CLI like upstream `nixos`'s `lab` (`cli/`: cobra, the Cloudflare, OpenBao, Forgejo and Kubernetes SDKs, tests) replacing the shell scripts (`cloudflare-credentials`, `rotate-state-passphrase`, `onboard-user`) once they grow or get hard to test; port upstream's commands where they match.
- Progressive delivery with Argo Rollouts and Istio (already serving the Gateways and the mesh) splitting traffic by weight: canary or blue-green for stateless apps with two or more replicas (blog, homepage). Today Argo CD applies plain updates: app-template's default `Recreate` (most apps have one replica on a `ReadWriteOnce` PVC), `RollingUpdate` in upstream charts; rollback is a git revert.
- A pull-through registry cache for the sandbox (a k3d registry outside the cluster, kept across `make dev-clean`): the node's containerd keeps its images inside the cluster, so every `make dev-fresh` downloads them all again, and slow or flaky pulls stretch the first sync past the tests' waits.
- An external dead man's switch (e.g. healthchecks.io) for the Watchdog: ntfy's delayed message cannot fire when ntfy, the Tunnel or the cluster is down.
